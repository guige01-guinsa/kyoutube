# 출시 전 관리 기능 확대 검토 — 2026-09-30

> 이후 사용자의 명시적 승인을 받아 구현했다. [최신 구현·검증 보고서](owner-management-completion.md)를 참조한다. 아래 거절 이력과 ‘적용되지 않음’은 승인 이전 상태다.

사용자는 출시 전 기록 보존을 필수 조건에서 제외하고, 과거 거래 삭제와 임의 단위 변경도 시스템 무결성에 심각한 문제가 없으면 구현하도록 요청했다. 이전 보고서의 ‘기록 보존 때문에 제외’ 방침은 이번 요청에 적용하지 않는다.

## 실제 진행 상태

- 기존 0076/0077 및 앱 구현은 유지했다. 새 삭제/환산 마이그레이션과 화면은 적용되지 않았다.
- 새 `management_dependency_checks.cjs`를 기존 격리 DB 검사에 연결했다. 총 355개 검사 통과. 운영 DB 쓰기 0건.
- 두 차례 코드 적용이 자동 승인 검토에서 거절되었다. 이유: 광범위한 영구 삭제와 재고 변경의 연결 관계 안전성이 충분히 입증되지 않음. 거절된 코드를 다른 도구로 적용하거나 실행하지 않았다.
- 운영 배포, 운영 데이터 삭제, 새 Android 빌드를 수행하지 않았다. 이번에는 앱 코드 변경이 없어 Flutter 전체 검사를 재실행하지 않았다.

## 확인한 연결 관계

| 대상 | 확인한 영향 | 추가로 처리할 조건 |
|---|---|---|
| 개인 구매요청서 | 상태 이력과 거래 평가가 함께 삭제된다. 재고 테이블 외래키는 없다. | 삭제 표식으로 지연된 생성 재시도 차단. 외부 공급업체에 이미 전달한 문서는 자동으로 취소되지 않는다고 안내. |
| 업소 구매요청서 | 문서 버전·구매 근거·공급업체 사본·입고 마감은 함께 삭제. 입고 수불은 요청서 연결만 해제되고 현재고는 유지. | 식단/일괄 구매 결과 JSON에 남은 요청서 링크의 표시 처리. 재시도로 같은 발주가 중복 생성되지 않는지 검사. |
| 개인 매출 | 재고와 외래키로 연결되지 않음. 집계는 저장된 매출 기준. | 본문과 이력 삭제 후 합계 검증. 요청 키는 재생성 방지 표식으로 유지. |
| 공동 공급업체/취급상품 | 취급상품·기본 구매 연결은 연쇄 삭제 가능. 이미 발행된 문서는 독립 사본을 가짐. | 기본 구매 연결 해제 안내, 이전 화면에서 저장하는 지연 요청 차단. |
| 재고 단위 | 입고 환산값, 수불 수량, 예약 원수량과 잔량, 레시피 기본 연결에 영향. | 예전 단위 화면에서 추가 입고/실사/사용을 입력하지 못하게 해야 함. 구매 포장 수량과 금액은 별도 유지. |
| 재고 품목 삭제 | 수불·예약이 함께 삭제되고 레시피 기본 연결은 외래키가 삭제를 제한함. | 살아 있는 요청서가 다시 미입고로 보이면 중복 입고 가능. 예약 또는 입고 문서의 연관 처리 없이 단독 삭제하지 않음. |

## 다음 구현 설계

1. 보관/복원은 기존 관리 권한으로 유지한다. 영구 삭제는 개인 소유자 또는 업소 소유자만 실행하는 별도 경로로 둔다.
2. 삭제 전 서버가 대상 수정 번호와 연결 목록, 사라질 이력, 유지되는 재고를 계산하여 미리보기를 반환한다. 임의 ID 목록을 클라이언트에서 전달해 연쇄 삭제하지 않는다.
3. 확인 당시 연결 정보의 검증값을 실행 요청에 포함한다. 권한·수정 번호·연결 정보가 바뀌면 전체 작업을 취소하고 다시 확인한다. 요청서 저장과 같은 잠금 순서를 사용한다.
4. 삭제된 ID/요청 키에는 최소한의 재실행 차단 표식만 남긴다. 거래 내용과 감사 기록 보존을 강제하지 않는다. 실제 외부 주문의 취소/환불 기능과는 구분한다.
5. 단위 변경은 `기존 1단위 = 새 단위 몇 개`를 입력하고 현재고·예약량의 전후 값을 보여준다. g↔kg, mL↔L은 검증된 비율을 제안한다. 개↔g, 봉↔kg 등은 사용자 확인 비율을 요구한다.
6. 단위 변환 시 구매 포장 수량/가격은 바꾸지 않고 재고 환산 계수만 대응시킨다. 소수점 6자리나 허용 범위 밖의 결과를 반올림해 강행하지 않는다. 기존 단위로 열린 화면의 쓰기를 서버에서 거절하는 설계가 포함되어야 한다.
7. 활성 예약과 요청서 연결이 남은 재고는 우선 어떤 업무까지 함께 정리할지 미리보기에서 선택하도록 설계한다. 시스템 연결을 잘못 남기는 삭제는 기록 보존 여부와 관계없이 실행하지 않는다.

## 구현 완료 전에 필요한 동작 검증

- 소유자/직원/다른 계정/익명 계정별 권한, 삭제 중 계정 전환.
- 삭제 미리보기 후 연결 변경, 같은 삭제 요청 재시도, 삭제한 ID의 지연 저장.
- 삭제 후 개인·공동 매출 집계, 부분 입고/반품, 살아 있는 요청서의 중복 입고 방지.
- 식단·일괄 구매 결과의 삭제된 요청서 표시와 재시도.
- g→kg→g, L→mL, 사용자 지정 개→g, 환산 불가·정밀도 초과, 단위 변경 중 열린 예전 화면.
- 기존 수불과 예약의 전후 일치, 기본 구매 연결 재확인, 트랜잭션 중 실패 시 전체 복구.
- 새 화면의 모바일/웹, 큰 글자, 오류·취소 흐름. 마지막에 고정 Flutter SDK로 정적 분석과 전체 테스트.
