# 관리 기능 개편 실행 계획

> 이후 승인된 영구 삭제·재고 단위 변경은 [최신 구현·검증 보고서](owner-management-completion.md)에 기록했다. 해당 기능의 제외 방침은 최신 승인 범위에서 대체되었다.

2026-09-30. 사용자 승인으로 `management-crud-review.md`의 안전한 개선 범위를 단계별 구현한다.

## 사용 방법

| 관리 대상 | 사용할 동작 |
|---|---|
| 개인 구매처 | `수정` 또는 `관리(···) → 보관·복원`. 보관한 구매처는 기존 기록 정리의 보관함에서 복원 |
| 업소 공동 거래처·상품 | 거래처/상품의 `관리(···)`에서 사용 중지·다시 사용. 상품은 `규격 복제` 후 수정 |
| 공급업체의 공개 상품 | `관리(···) → 복사해서 만들기 / 판매 중지 / 판매 재개`. 복사본의 가격·판매 여부는 직접 확인 |
| 구매요청서 | 상세의 `관리(···) → 보관·복원`. 개인의 미전달 초안에만 `초안 삭제` 표시 |
| 저장한 구매 계획 | `요일·저장 계획 → 구성 수정 / 복사해서 만들기 / 관리`. 구성 수정 후 `변경 저장`, 별도 계획은 `다른 계획으로 저장` |
| 재고 품목 | `관리(···) → 관리 메모 수정`. 목록의 `현재고·예약이 없는 품목 숨기기` 사용 |
| 개인 매출 | `수정` 시 정정 사유 입력. `관리(···) → 처리 이력 / 매출 취소`. `취소한 매출 보기`에서 복원 |

다음 운영 배포 후 위 동작을 사용할 수 있다. 보관·사용 중지는 과거 기록을 보존한다. **매출 취소만 집계에서 제외되며**, 복원하면 집계에 다시 포함된다.

## 단계와 완료 기준

1. 거래 기록 보호와 공통 관리 동작: 개인 요청서의 전달/입고 이력 영구 삭제 차단, 안전한 초안 삭제, 상세에서 보관/복원, 거래처·상품의 빠른 상태 변경과 복제.
2. 저장한 구매 계획 관리: 기존 계획 수정, 이름 변경, 복제, 보관/복원, 검색과 상태 구분. 과거 발주·재고 예약은 유지.
3. 관련 영역 정리: 재고 품목 메모와 목록 정리, 레시피·메뉴·식단·직원의 기존 상태 관리 접근성, 원가·매출의 정정/취소 의미와 이력 보완. 재고의 사용 중지/재개는 예약·구매 연결까지 검토하여 안전한 범위를 결정. 입고·수불 덮어쓰기와 임의 단위 변환은 제외.
4. 검증과 인계: 격리 DB의 권한/상태/경합/구형 클라이언트/참조 보존 검사, Flutter 정적 분석과 전체 테스트, 웹·모바일 크기 확인. 배포 순서와 호환성 문서화.

각 단계는 실행 계획에 결과와 미포함 사유를 기록한다. 기존 마이그레이션은 수정하지 않는다. 기존 개인/업소/공개 공급업체의 소유권과 공개 범위는 유지한다. 배포용 AAB는 현재 제공한 v90을 덮어쓰지 않는다.

## 진행

### 1단계 — 구현 완료

- 공통 `관리` 메뉴에서 한 번에 하나의 작업만 수행하고 실패를 표시한다. 확인창은 계정 전환 시 닫힌다.
- 개인 거래처: 수정 유지, 보관·복원을 목록에 연결. 영구 삭제 대신 기존 0074 보관함을 사용하며 구형 앱의 직접 DELETE도 차단한다.
- 공동 거래처·상품: 수정 번호를 확인하는 기존 저장 RPC로 사용 중지·재개. 상품 규격 복제는 새 ID와 사용 중지 상태로 시작한다. 상품명·규격 검색 및 중지 상품 포함 선택을 추가했다.
- 공개 공급업체 취급상품: 판매 중지·재개, 복사, 상품명·브랜드 검색. 복사본은 판매 중지 상태이고 가격·유효일을 비워 재확인하게 한다. 기존 사진의 소유권과 참조 보호는 유지한다.
- 개인 구매요청: 전달 이력이 전혀 없는 초안만 삭제한다. 서버가 수정 번호, 소유자, 전체 상태 이력, 평가 참조를 확인한다. 삭제 표식을 남겨 지연된 생성 요청의 재실행으로 초안이 살아나지 않게 한다. 저장 RPC와 같은 잠금 순서를 사용한다.
- 개인/업소 요청서 상세: 초안·입고완료·취소 상태에 보관·복원을 제공한다. 전달 중 자료는 기존 완료 절차를 거친다. 입고·승인·전달 내역은 삭제하지 않는다.

### 2단계 — 구현 완료

- `요일·저장 계획`에서 검색, 이름 변경, 구성 수정, 복사, 보관, 복원을 제공한다.
- 구성 수정은 원래 ID와 수정 번호를 사용한다. 복사 저장은 새 ID를 사용한다.
- 저장 당시 메뉴가 바뀌었으면 현재 메뉴·인분을 다시 고르게 한다. 보관된 계획은 복원 후 사용한다.
- 계획 정의만 변경한다. 이미 생성한 발주·예약·식단의 사본은 유지한다.
- 기존 보관 한도(계획 100개 등)는 유지한다. 보관은 영구 삭제나 한도 우회가 아니다.

### 3단계 — 구현 완료 / 위험한 범위 제외

- 재고: 보관 위치 등 관리 메모 편집, 메모 검색, 현재고와 예약이 모두 0인 품목 숨김을 제공한다. 메모는 별도 수정 번호로 충돌을 확인한다.
- 개인 매출: 날짜·수량 정정에 사유와 수정 번호를 요구한다. 삭제 대신 취소·복원하며 취소한 매출 조회와 최근 100건의 처리 이력을 제공한다. 전후 값과 사유를 서버에 남긴다. 취소는 집계에서 제외, 복원은 재포함하며 판매 당시 단가·원가와 재고는 바뀌지 않는다.
- 공동 거래처·상품·계획 및 재고 메모의 변경 동작은 서버 관리 이력에 남는다. 기존 거래 문서/재고 수불 이력과는 분리한다.
- 레시피·메뉴·식단·직원·제휴상품은 기존 수정/복사/중지/보관/승인/복원 기능을 재사용한다. 동일 기능을 별도 메뉴로 중복 생성하지 않았다.
- **제외:** 재고 품목의 영구 삭제·이름/단위 일괄 변경·사용 중지, 입고 이력 덮어쓰기, 완료 거래 연쇄 삭제, 승인 없이 거래 상태 되돌리기. 재고가 0이어도 예약·미완료 발주·기본 구매 규칙의 참조가 남을 수 있어 목록 숨김과 사유 있는 실사/반품/예약 해제를 사용한다.
- 공유 원가·매출의 기존 버전 이력과 취소/보관 의미는 유지한다. 취소한 실제 거래를 단순한 목록 복원으로 재실행하지 않는다.

### 4단계 — 검증

- 초기 환경 점검 완료. pinned Flutter 3.44.8, JDK 17 사용.
- 격리 PGlite PostgreSQL 계약 검사 345개 통과, 운영 DB 쓰기 0건. 실제 기존 마이그레이션 위에 0076/0077을 적용했다.
- 소유권·직원 권한·익명 계정·수정 충돌·구형 앱 직접 삭제 차단·재시도·삭제 후 재생성 차단·원본 보존·매출 집계·계정 삭제를 확인했다. 다중 연결 부하 시험 대신 수정 번호 충돌과 동일 잠금 순서를 확인했다.
- 신규 화면 흐름 및 한/영 UI 문구 검사 통과. 필수 `tools/dev/verify.ps1` 실행 후 기존 영구 삭제를 기대하던 테스트 1건을 새 보관 동작/원본 보존 검증으로 갱신했다. 최종 정적 분석 오류 0건, 전체 Flutter 테스트 **775개 통과, 기존 선택 실행 테스트 4개 제외**. 전체 최종 실행 종료 코드 0.
- 좁은 모바일 화면과 큰 글자, 데스크톱 화면에서 기존 구매·재고·공급업체 관리 흐름을 함께 검사했다. 연결된 실제 Android 기기나 운영 계정을 이용한 검사는 수행하지 않았다.

## 운영 적용 순서와 호환성

1. 운영 백업/복구 지점을 확인하고 0076, 0077을 순서대로 적용한다. 기존 마이그레이션을 수정하거나 DB를 초기화하지 않는다.
2. 스키마 갱신 후 새 웹을 배포하고 관리 권한별로 계획 저장·거래처 보관·매출 취소/복원을 확인한다.
3. Play Console에 이미 사용한 버전 코드를 확인한 뒤 새 AAB를 생성한다. 기존 v90 파일과 서명 키는 유지한다.
4. 구형 앱의 개인 거래처/요청서/매출 직접 삭제 및 매출 직접 수정은 안전하게 거절된다. 구형 앱에서도 취소된 개인 매출은 조회·집계에서 제외된다. 구형 앱은 저장 계획의 보관 상태를 구분하지 못하므로 새 앱 업데이트가 필요하다.
5. 오류 대응 시 새 이력·보호 정책을 제거하는 역방향 변경 대신 수정 마이그레이션을 사용한다. 이 작업에서는 운영 적용·배포·AAB 생성은 실행하지 않았다.

환경 점검에서 기존 PATH의 전역 Flutter 경고, Android 라이선스 상태 확인 불가, Windows용 Visual Studio 구성 미완료가 보고되었다. 실행은 저장소의 고정 SDK로 수행했다. Android 출시 작업 시 라이선스 환경을 다시 확인한다.
