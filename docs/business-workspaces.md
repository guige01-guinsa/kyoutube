# 담당 업무별 화면과 업소 공동 자료

개발 검증: 2026-09-18. 운영 반영: 2026-09-19. 사용자 승인으로 DB 0062와 v74 웹 배포를 완료하고 1.0.1+74 서명 AAB를 생성했다. Google Play 업로드는 별도다. [v74 출시·검증 기록](release-v74.md).

## 사용자 흐름

- 업소·전문가용의 **담당 업무 설정**에서 구매·조리·경영을 여러 개 선택하고 기본 화면을 정한다. 이는 화면 선호 설정이다.
- **업소 공동 업무 → 업소 만들기**에서 사장이 업소 이름과 표시 이름을 입력한다. 업소 책임자의 활성 Business 이용권을 서버에서 확인한다.
- **직원·권한 관리 → 직원 초대하기**에서 직원의 로그인 이메일을 입력하고 기본 역할 또는 개별 권한을 선택한다.
- 초대 코드를 직원에게 직접 전달한다. 코드는 인증된 이메일과 일치해야 하고 24시간 이내 한 번만 사용할 수 있다. 서비스가 자동으로 이메일/카카오톡을 발송하지 않는다.
- 직원은 자기 계정으로 로그인하고 **초대 코드로 참여**를 누른다. 직원 개인의 유료 결제를 요구하지 않고 업소 책임자의 이용권과 부여된 권한으로 공동 업무를 사용한다.
- 여러 업소에 참여하면 업소 목록에서 선택한다. 모든 조회·수정·출력은 선택한 업소 ID로 제한한다.

## 기본 권한

| 업무 | 공동 레시피·식단 | 공동 구매·입고 | 공동 원가·판매 | 구매 승인 | 직원·권한 관리 |
|---|---|---|---|---|---|
| 구매 담당 | 조회 | 조회·수정 | 접근 불가 | 불가 | 불가 |
| 조리 담당 | 조회·수정 | 조회 및 재료 전달 | 접근 불가 | 불가 | 불가 |
| 경영 담당 | 조회 | 조회 | 조회·수정 | 가능 | 불가 |
| 사장 | 조회·수정 | 조회·수정 | 조회·수정 | 가능 | 가능 |

사장은 체크박스로 겸임 권한을 조합할 수 있다. 수정 권한에는 조회 권한이 필요하며 승인 권한에는 구매 조회가 필요하다. 본인 사장 권한은 이 화면에서 제거할 수 없다. 메뉴 선호, 계정 메타데이터, 임의 역할 문자열은 서버 권한을 부여하지 않는다.

## 업무 연결

1. 조리 담당자가 공동 레시피의 재료·조리법·기준 인분을 저장하고 변경 이력을 관리한다. 여러 공동 레시피를 연결해 날짜·예정 인분별 식단 계획을 작성할 수 있다.
2. **구매 준비로 넘기기**는 재료 문자열을 구매 초안으로 전달한다. 구매 수량과 단위는 비워 둔다. 구매 담당자가 품명·수량·구매 단위를 따로 확정한다.
3. 구매 담당자가 공급업체, 납품 주소/희망일, 품목별 구매 수량·단위·단가·규격을 작성한다. 모르는 단가는 비워 둘 수 있다.
4. 기본 흐름은 **작성 중 → 승인 대기 → 승인 완료 → 전달 확인 → 입고 확인**이다. 승인 대기 이후에는 직접 편집할 수 없고 작성 중으로 돌려 수정 후 다시 승인한다. 사장은 소규모 업소를 위해 승인 단계를 끌 수 있다.
5. 구매요청서 PDF 미리보기·공유·인쇄는 기존 문서 기능을 재사용한다. 승인 전 문서에는 검토용 초안 문구를 표시한다. 출력 직전 서버가 접근 권한과 문서 버전을 다시 확인한다. 파일을 내보내거나 공유창을 연 사실만으로 실제 전달·입고를 확정하지 않는다.
6. 경영 담당자는 1인분 원가·판매가를 공동 기준으로 등록하고 판매 날짜/수량을 기록한다. 서버가 당시 가격·원가를 복사해 과거 매출을 보존한다. 일/주/월과 KRW/USD별 매출·원가·예상 이익을 조회한다. 입력하지 않은 경비·세금까지 포함한 순이익 계산은 아니다.
7. 잘못된 비구매 자료는 **사용 중지**하며 변경 이력은 남긴다. 중지한 판매 기록은 집계에서 제외한다. 구매는 별도의 취소 상태로 관리한다.

## 기존 기능과의 관계

- 기존 개인 레시피·장보기·셰프 배합·거래처·구매 대장 및 그 RLS는 유지한다. 공동 자료는 별도 저장 공간이다.
- 개인 레시피는 소유자가 선택한 재료·조리법·팁만 사본으로 공유한다. 사진·사업자등록증 파일 경로는 자동 공유하지 않는다. 복사한 레시피의 기준 인분은 확인·수정해야 한다.
- 공동 원가는 현재 확정된 **1인분 원가·판매가 입력** 방식이다. 기존 개인 셰프 작업실의 재료별 단가·수율 계산을 직원 공동 자료로 자동 동기화하지 않는다.
- 공동 구매요청의 공급업체·구매 품목은 직접 작성한다. 기존 개인 구매 화면의 공개 업체 비교/후보 선택 기능은 계속 이용할 수 있지만 공동 요청과 자동 연동하지 않는다.
- 조리량 자동 재고 차감, 재고 실사, 결제, 배송 추적, 공급자 답변 자동 수신, 직원 초대 자동 발송은 추가하지 않았다. 입고는 담당자의 확인 기록이다.
- 구매/조리/경영 튜토리얼을 각각 6/5/3개로 분류했다. 기존 실습 예제와 진행 기록 ID는 유지했다.

## 보안·동시 수정

- 새 migration: `supabase/migrations/0062_business_workspaces.sql`. 새 Edge Function이나 비밀 키는 필요 없다.
- 6개 테이블에 RLS를 적용한다. 인증 사용자의 직접 쓰기는 금지하고 명시적 RPC에서 업소·회원·권한·Business 이용권·입력 형식·현재 버전을 검증한다.
- 모든 변경은 업소 행을 잠그고 처리한다. 자료 수정에는 예상 revision이 필요하며 다른 직원이 먼저 저장하면 덮어쓰지 않고 최신 자료 확인을 안내한다.
- 초대 토큰은 서버에 SHA-256 해시만 저장하고 해시 조회 권한도 주지 않는다. 초대/권한 변경/가입/접근 해제/설정 이력은 사장만 조회한다.
- 접근 해제는 서버의 다음 요청부터 적용된다. 열린 화면의 권한은 60초 주기로 갱신하고 저장·PDF 출력 시 다시 검사한다. 이미 사용자가 다운로드한 파일을 원격 회수할 수는 없다.
- 로그아웃/계정 전환 시 자료 화면·입력창·초대/선택 창을 닫거나 무효화한다. 개인 계정의 캐시를 다른 계정에 넘기지 않는다.
- 업소당 활성 회원 30명(사장 포함), 자료 3,000건, 소유 업소 3개, 시간당 초대 30건, 구매 품목 100개, 식단 연결 20개로 제한한다. 초대와 복구 모두 회원 수 한도를 검사한다.
- 책임자의 이용권 만료 시 공동 쓰기/승인/원가·매출 열람을 차단한다. 기존 레시피/구매 조회와 사장의 접근 해제 기능은 유지한다.
- 사장 계정 삭제 시 해당 소유 업소와 공동 자료도 FK cascade로 삭제된다. 업소 소유권 이전과 별도 자료 보존 정책은 후속 확장 대상이다.

## 검증과 재현

실제 Docker Supabase PostgreSQL 17.6의 **별도 테스트 DB**에서 57개 권한/업무 계약 검사를 통과했다. 인증 사용자와 기존 레시피 테이블은 격리된 fixture이며 기존 membership snapshot SQL과 pgcrypto를 사용한다. 실제 Google 로그인이나 운영 데이터 테스트 결과로 해석하면 안 된다. 생성한 임시 DB만 제거하며 운영 DB나 기존 로컬 DB 자료는 변경하지 않는다.

```powershell
npm.cmd install --prefix .artifacts/business-db-runtime --no-audit --no-fund --ignore-scripts @electric-sql/pglite@0.5.8 pg
node tools/test/business_workspaces_contract.cjs --docker
# Docker 없이 실행하는 보조 검사
node tools/test/business_workspaces_contract.cjs
powershell -ExecutionPolicy Bypass -File tools/dev/verify.ps1
```

주요 검사: 다른 업소 접근 차단, 이메일/만료/일회성 초대, 초대 해시 비공개, 직원의 권한 상승 차단, 승인 우회 차단, 변경 충돌, 전달 초안 중복 방지, 구매량 누락 검증, 재무 자료와 이력 제한, 직원 복구 한도, 접근 해제 후 PDF 재검사, 과거 판매 가격 보존, 취소 판매 집계 제외.

최종 정적 분석 오류 0개, Flutter 자동 테스트 467개 통과·기존 제외 4개를 확인했다.

Flutter 검증은 역할 메뉴/설정, 공동 저장/충돌, 읽기 전용 편집 차단, 저장 전 이탈 확인, 계정 변경, 재무 조회 권한 회수, 한국어/영어 모바일·데스크톱 및 200% 글자 확대를 포함한다. 상세 결과는 `.artifacts/business-verified.log`와 `.artifacts/business-docker-contract.json`에 기록한다.

## 운영 반영 및 실사용 확인

1. 완료: 암호화 백업을 별도 DB에 복원해 88개 테이블·4,779개 행을 확인했다.
2. 완료: 승인된 DB 0062만 운영 적용하고 기존 이력·개인 자료를 보존했다. 6개 테이블·22개 함수의 권한과 비로그인 차단을 확인했다.
3. 완료: v74 웹 배포와 1.0.1+74 서명 AAB 생성. 한영 브라우저 검사 22개 통과. Flutter 버전·서명 키·프로젝트 유지.
4. 후속 실사용 확인: 사장·구매·조리·경영 각 실제 테스트 계정으로 초대, 자료 공유, 승인, 출력, 권한 해제를 배포 환경에서 확인한다. 이번 배포 검사는 실제 운영 계정의 전체 흐름을 대신하지 않는다.

문제가 발생하면 웹은 Firebase Hosting의 이전 릴리스로 복구하고 새 공동 자료 테이블은 보존한다. Android는 이전 동작으로 복구한 코드에 더 높은 versionCode를 부여해 새 AAB를 배포한다. 0062의 테이블을 삭제하는 방식으로 되돌리지 않는다. 기존 개인 기능과 공동 데이터가 분리되어 있어 클라이언트 복구 중에도 새 공동 기록을 보존할 수 있다.

개발 환경의 Flutter doctor에는 PATH의 전역 SDK, Android SDK 라이선스 확인 및 Windows Visual Studio 구성 경고가 있다. 실제 분석/테스트에는 고정된 Flutter 3.44.8을 사용했고 Android 대상 JDK는 17이다. 실제 v74 Android 출시 빌드와 서명 검사는 JDK 17에서 통과했다.

운영 배포와 AAB 생성은 2026-09-19 사용자의 명시적 승인에 따라 완료했다. 상세 산출물과 검증 범위는 [v74 출시 기록](release-v74.md)에 남겼다.
