# 3차 개편: 품목별 입고·반품, 재고와 조리 예약

> 2026-09-22: 이 문서의 기능은 v79 통합 운영 배포와 새 서명 AAB에 포함되었다. 아래 소스 단계의 미배포 설명은 당시 기록이다. [최종 배포·검증](release-v79.md) · [메뉴 기반 빠른 구매](business-menu-fast-purchase.md).

구현일: 2026-09-21. **소스 구현 단계이며 운영 DB·웹·Android AAB에는 아직 적용하지 않았다.** 기존 1차 사용자 영역 정리와 2차 공동 거래처·상품 연결을 이어서 사용한다.

## 업무 흐름

메뉴·레시피 → 필요량 계산 → 현재 재고·진행 중 요청 조회 → 사용 가능 재고·입고 예정량 확인 → 구매 초안 → 승인·실제 전달 → 품목별 검수·부분 입고 → 반품/잔량 확인 → 입고 마감 → 조리용 예약·실제 사용 기록.

구매 초안 작성은 재고를 자동으로 예약하거나 차감하지 않는다. 판매 기록도 재고를 자동으로 차감하지 않는다. 실제 활동을 기록한 수량만 재고에 반영한다.

## 사용자별 화면

| 업무 | 필요한 서버 권한 | 동작 |
|---|---|---|
| 재고·입고·예약·수불 조회 | `purchasing.read` | 동일 업소의 공동 자료 조회 |
| 품목 등록, 실사/폐기 조정, 입고, 반품, 입고 마감 | `purchasing.read` + `purchasing.write` | 구매담당자 또는 해당 권한을 받은 직원 |
| 조리용 예약, 실제 사용, 예약 해제 | `purchasing.read` + (`recipes.write` 또는 `purchasing.write`) | 조리담당자·구매담당자 |

사장은 기존 업소 권한 규칙을 따른다. 화면에서 선택한 역할/사용 목적은 권한을 부여하지 않는다. 경영담당자의 기본 권한에는 재고 조정이나 입고 권한이 없다. 이용권 만료 시 비재무 조회는 유지하되 기록을 추가할 수 없다. 접근이 철회되면 조회도 차단한다.

진입점:

- 업소 업무홈 또는 구매·입고 → **재고·조리 예약**.
- 전달 확인된 구매요청 상세 → **품목별 입고·반품**.
- 재고 품목 상세 → **실사·재고 조정**, **조리용 예약**, **실제 사용 기록**, **남은 예약 해제**.

경로는 `/business-workspaces/:workspace/inventory`, `/inventory/:item`, `/receiving/:request`를 사용하며 모두 공동 업무의 구매 영역으로 표시한다.

## 수량 처리 원칙

- 재고 품목은 업소·이름·규격·단위로 구분한다. 앞뒤 공백과 영문 대소문자만 정규화한다. g와 kg, 손질 전후 규격은 서로 다른 품목이다. 품목명·규격·단위는 등록 후 변경하지 않는다.
- `현재고 = 수불 증감 합계`, `예약량 = 활성 예약의 남은 수량 합계`, `사용 가능 = 현재고 - 예약량`.
- 실사 조정은 **현재고의 최종 값이 아니라 증감량**을 입력한다. 예: 현재 8kg, 실측 7kg이면 -1kg. 기초 재고·실사 차이·폐기 사유를 남긴다.
- 예약은 현재고를 바꾸지 않고 사용 가능량을 줄인다. 실제 사용은 현재고와 남은 예약량을 같이 줄인다. 남은 예약 해제는 현재고를 바꾸지 않는다.
- 음수 재고, 예약 초과, 예약된 물량을 사용하는 조정·반품을 서버에서 차단한다. 각 기록에 용도·사유가 필요하다.
- 수량과 환산 계수는 최대 소수 6자리, 최대 10억으로 제한하며 반영되는 재고량도 동일 정밀도를 만족해야 한다. 자동 단위 변환이나 반올림으로 맞추지 않는다.

## 입고·반품과 마감

1. 승인된 요청을 공급업체에 실제 전달한 뒤 기존 **전달 확인**을 기록한다.
2. 재고 품목이 없으면 먼저 등록한다. 원래 요청의 품목을 선택하고 실제 도착한 구매 수량, 반영할 재고 품목, 구매 1단위당 재고량을 확인한다.
3. 예: 요청 4봉, 1봉=500g, 실제 도착 2봉이면 현재고 +1,000g, 순입고 2봉, 미입고 2봉이다. 첫 입고에서 선택한 재고 품목과 환산 계수는 후속 입고에도 고정한다.
4. 반품은 **원래 입고 기록**에서 기록한다. 반품 가능한 잔량을 표시하며 원래 구매 단위와 고정 환산 계수를 사용한다. 이미 반품했거나 조리 예약으로 확보된 수량을 초과할 수 없다.
5. 입고 기록만으로 요청서를 마감하지 않는다. **입고 마감**에서 잔량을 확인한다. 미입고가 남아 있으면 수량을 명시적으로 수락하고 사유를 적어야 한다. 마감 시점의 품목·수량과 사유를 보존한다.
6. 마감 후 반품은 가능하지만 요청을 자동으로 다시 열지 않는다. 교환·추가 납품은 새 요청으로 관리한다. 일부 입고 후 요청을 취소해도 물리적 재고는 남아 있으며 실제 반품을 따로 기록한다.

이전 방식의 `received` 상태는 **과거 재고로 자동 환산하지 않는다**. 기존 요청에는 이전 방식이라는 안내를 표시한다. 도입 시 실제 보유량을 실사해 증감 기록으로 등록한다. 새 마감도 기존 `received` 상태를 사용하지만 별도 마감 스냅샷으로 구분한다.

## 구매 중복 확인의 범위

- 메뉴 구매 화면에서 재료별로 이름·규격·단위가 정확히 같은 재고의 현재고·예약량·사용 가능량을 표시한다.
- 같은 재료를 원래 구매 기준에 포함한 진행 중 요청을 최근 5개까지 보여 준다. 마감·취소된 요청은 제외한다. 이는 **작성 당시 기준**이며 이후 수정된 실제 주문 품목/수량을 완전히 대조한 결과가 아니다.
- 사용자는 요청서를 열어 공급업체·품목·납품일을 확인한다. 입고 예정량을 추정하거나 구매량에서 자동 차감하지 않는다. 기존 직접 작성 요청이나 다른 단위/이름으로 된 요청은 이 경고에서 누락될 수 있다.
- 조회 실패 시 오류와 재조회 버튼을 표시한다. 실패를 재고 0으로 간주하거나 이미 입력한 구매량을 바꾸지 않는다.

## 서버·데이터 보호

새 마이그레이션은 `0069_business_inventory.sql`이다. `0062`, `0067`, `0068`의 공동 업무 및 메뉴·거래처 기능을 전제로 한다. 선택적 직원 프로필 마이그레이션 `0064`의 운영 적용을 요구하지 않는다.

- 품목, 수불, 예약, 마감 테이블은 업소별 RLS를 적용한다. 인증 사용자의 직접 쓰기 권한은 없다.
- 변경은 단일 RPC `business_stock_action`에서 업소 행 잠금, 권한, 수량, 원본 구매/예약 버전을 검증한 후 한 트랜잭션으로 기록한다.
- 수불은 수정·삭제하지 않는다. 재고 조정 또는 반품으로 보정하며 원본 기록을 남긴다. 실제 주문/결제나 공급업체에 메시지를 전송하는 기능은 없다.
- 변경 ID·계정·내용을 기록해 동일 요청의 통신 재시도는 중복 처리하지 않는다. 권한은 재시도에서도 다시 검사한다. 결과가 불명확하면 화면 입력을 고정해 같은 내용으로 재시도한다. 확정된 DB 오류는 입력을 보존한 채 수정할 수 있게 한다.
- 기존 구매 상태 전환 RPC의 직접 `received` 전환은 차단한다. 구버전 앱은 새 입고 마감 기능을 사용할 수 없으므로 DB 적용 시 새 웹/앱과 함께 배포하고 구버전에는 웹 사용 또는 업데이트를 안내해야 한다.
- 품목은 업소당 1,000개, 활성 예약은 업소당 1,000개까지 허용한다. 수불 이력은 50개씩 조회한다. 수불·예약에는 기록자 ID와 기록 시간이 남는다.
- 추가 AI 호출·AI 이용료·요금제 변경은 없다. 실제 사용량에 따른 DB 저장/조회 부하는 추가된다.
