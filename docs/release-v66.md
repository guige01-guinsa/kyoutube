# Recipe Scout v66 — 2026-09-15

사용자 승인으로 DB **0059**, **delete-account 함수 1개**, **운영 웹**, **1.0.1+66 production 서명 AAB** 반영·생성을 완료했다. Google Play 업로드와 휴대폰 설치는 수행하지 않았다.

추가 운영 수정: 웹 장보기 생성의 `Idempotency-Key` CORS 허용 누락을 수정하고 [recipe_api 서버 함수 v54 배포·검증을 완료했다](shopping-web-cors-hotfix.md). 장보기 쓰기 요청 사전 검사를 추가한 공개 웹 검사 9개도 통과했다. 아래는 최초 v66 배포 당시 검증 기록이다.

## 사용 흐름

1. 구매처 화면의 **공개 업체에서 내 거래처 선택** 또는 상단 더보기로 업체 검색을 연다. 업체는 **내 업체 등록**에서 기본 정보·취급 상품·사진을 입력하고 공개 여부를 결정한다.
2. 구매자는 품목 대/소분류·배송 지역·원산지·브랜드·가격·평점으로 찾는다. 공개 업체 선택 시 내 거래처에 중복 없이 추가하며, 해당 재료를 취급하는 내 거래처를 우선 표시한다.
3. 장보기 도우미의 **재료별 업체 선택 · 구매요청 초안**에서 재료마다 최대 3개 후보 업체를 선택한다. 전체 거래처 수가 3개로 제한되는 것은 아니다.
4. 재료 선택 완료 후 **최소 거래처 수 / 최저 구매가격 / 평점 우선** 중 하나로 초안을 만든다. 사용자가 최종 수정·저장하고 공유를 실행한다.

구매 수량과 판매 포장 내용량을 기준으로 비교하며 조리 수량·재고를 차감하지 않는다. 유효 가격·배송비·세금이 없는 경우 견적 필요로 표시한다. 후보 조합이 많으면 제한 탐색임을 표시하므로 항상 전역 최저가를 보장하지 않는다. [등록·계산·권한 상세](supplier-marketplace.md).

## 운영 배포와 보안 검증

- DB0059만 한 트랜잭션으로 적용했다. 0057 사전 모집은 함께 적용하지 않았다. 함수 9개의 운영 본문·권한·search_path, 새 테이블 RLS, 비공개 이미지 버킷, 거래처 중복 방지와 연결값 위조 차단을 확인했다.
- 기존 구매요청서 함수와 구매자 RLS 정책, 다른 마이그레이션을 유지했다. 운영 고객 자료나 테스트 계정을 생성·삭제하지 않았다.
- 계정 삭제 함수 **v24**만 배포했다. 이전 소스를 보관했고 로컬의 전체 상대 import 그래프와 실제 배포 소스가 일치한다. 기존 함수 내부 사용자 인증을 유지했다. 미인증/익명/잘못된 토큰 401, CORS 200, 잘못된 메서드 405 확인. 실제 운영 계정 삭제는 실행하지 않았다.
- [운영 웹](https://recipe-scout-workspace.web.app/)은 v66과 동일 소스다. 공개 파일 해시·보안 헤더·한국어/영어 PC/모바일·로그인 화면 및 인증 CORS 검사 8개, 두 도메인의 Google/Kakao PKCE 연결 검사 4개, 신규 업체 화면 3개의 한영 로그인 보호/로그인 이동 검사 6개를 통과했다. 실제 계정의 소셜 로그인 완료와 업체 사진 업로드·카카오톡 수신은 아직 검증하지 않았다.

## 남은 확인과 복구

Google Play Console 테스트 트랙에 v66 AAB를 업로드한 뒤 기존 앱을 업데이트한다. 휴대폰 설치는 사용자가 직접 진행한다. 실제 업체/구매자 계정으로 사진 등록·공개·내 거래처 선택·재료별 초안·최종 공유 수신을 확인해야 한다. 사업자 인증 서류 검토 화면과 평점 부정 이용 관리, Play 실제 결제 활성화, 사전 모집 백엔드는 별도 후속 작업이다.

문제 발생 시 신규 업체의 공개를 중지하거나 웹을 이전 Firebase Hosting 버전으로 되돌릴 수 있다. 함수의 배포 전 소스는 ignored `.artifacts/v66-function-backup-*`에 보관했다. DB0059의 테이블·이미지·요청서 연결을 삭제하는 롤백은 자료 손실 위험이 있으므로 새 수정 마이그레이션으로 복구한다. 자동 발송이나 자동 결제는 수행하지 않는다.
