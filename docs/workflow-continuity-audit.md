# 업무 흐름 연속성 점검

점검일: 2026-09-30

후속 구현: [업무 흐름 연속성 개선 결과](workflow-continuity-implementation.md). 아래 내용은 개선 전 점검 기록이다.

## 범위와 결론

현재 작업 폴더의 기능별 화면 코드 127개를 대상으로 오류, 빈 목록, 비활성 버튼, 선행 작업 안내를 검색하고, 관련 화면·공통 선택 창·라우터·일부 서버 검증을 추적했다. 구매 준비, 거래처·상품 선택, 요청서 승인과 쿠팡 구매, 입고·재고, 메뉴·식단, 일반 장보기, 제휴 상품 관리, 로그인·인증을 확인했다.

아직 개선할 지점이 있다. 대부분 필요한 기능 자체가 없는 경우보다는, 필요한 기능을 다른 곳에서 찾아 실행한 후 원래 작업으로 돌아와야 하는 경우다. 원인 안내와 함께 해결 동작을 제공하고, 입력값을 유지한 상태에서 해결 결과를 반영하는 방식이 적합하다.

이 문서는 **소스 기반 점검 결과**다. 실제 운영 계정·휴대폰의 모든 업무를 실행한 결과나 무결함 보증은 아니다. 현재 개발 중인 품명 검색과 일반 쿠팡 검색 경로도 포함하므로 운영 v92 화면과 차이가 있을 수 있다. 이번 점검에서는 제품 코드·DB·운영 배포·AAB를 변경하지 않았다. 실행 코드 변경이 없어 Flutter 전체 테스트도 다시 실행하지 않았다.

## 우선 개선 항목

우선도 1은 구매 업무의 핵심 경로 또는 인증 후 복귀에 직접 영향을 주는 항목, 우선도 2는 특정 조건에서 막히거나 불필요한 이동을 만드는 항목이다.

## 기능은 있으나 연결을 다듬을 부분

### 입고 품목 등록

입고 화면 상단에는 이미 `재고 품목 등록` 버튼이 있다 (`business_inventory_pages.dart:378–383`). 따라서 등록 기능이 없다는 판단은 맞지 않는다. 다만 재고가 하나도 없으면 각 품목의 입고 버튼은 이유 없이 비활성화된다 (`:469–472`).

품목 바로 옆에 `입고할 재고 품목이 필요합니다`와 `등록 후 입고`를 제공하고, 구매 품명·규격을 채운 등록 창에서 완료 후 원래 입고 품목으로 이어 주는 개선이 적절하다. 입고 창을 연 뒤 원하는 재고가 없다는 것을 알았을 때도 등록 경로가 필요하다 (`business_stock_form.dart:250–290`). 첫 입고 이후 품목·환산 기준 잠금은 유지한다.

### 단위 변경 안내 정합성

재고 등록 설명은 아직 “단위는 나중에 바꿀 수 없다”고 안내한다 (`business_stock_form.dart:219`). 하지만 소유자에게는 `재고 단위 변경` 메뉴가 있다 (`business_inventory_pages.dart:246`). 권한과 영향 검토 조건을 반영하도록 문구를 정정해야 한다. 단위 변경 후 재료·재고 연결을 다시 확인하라는 안내도 관련 연결을 여는 동작과 함께 제공하면 좋다 (`owner_record_management.dart:241–243`).

### 조리 완료 후 재고 사용

조리 완료와 실제 재고 사용 기록을 구분한 현재 설계는 유지할 필요가 있다. 조리 완료 안내는 별도 기록을 요청한다 (`business_meal_pages.dart:96–100`). 구매 준비 내역에는 이미 재고·예약 관리로 가는 버튼이 있다 (`:681–690`). 개선할 부분은 해당 식단의 관련 예약으로 바로 이동하고, 실제 사용·미사용 예약 해제를 확인하도록 연결하는 것이다. 조리 완료만으로 전량 사용 처리해서는 안 된다.

### 공급업체 검색 결과 없음

구매 후보 조회에서 검색어·지역 수정은 가능하지만 결과가 없을 때 업체 등록 요청은 설명만 있다 (`procurement_plan_page.dart:787–794`). `내 거래처 직접 등록` 또는 등록 요청 절차를 연결할 수 있다. 공개 공급업체 등록·심사와 개인 거래처 등록은 구분해야 한다.

## 이미 갖춰진 흐름 — 재사용할 부분

- 공급업체 상품 링크 입력에서는 실제 공급업체를 즉시 등록한 후 돌아와 자동 선택하는 구조가 있다 (`supplier_product_link_dialog.dart:178–205`). 거래처·상품 선택에도 이 패턴을 확장할 수 있다.
- 구매요청서 상세의 수정·작성 복귀·승인 동작이 존재한다. 쿠팡 화면에서는 이를 새로 구현하기보다 연결한다.
- 공통 구매 기준에는 상품 포장 환산 입력·표시·확인이 있다. 입고에도 환산 미리보기와 확인이 있다. 재고 연결 단위 차이는 별도의 문제로 다룬다.
- 최근 개발한 품명 후보 검색은 오류 시 재조회와 직접 입력을 지원한다 (`purchase_name_field.dart:96–111`). 후보가 없다는 이유로 입력 자체를 막지 않는다.
- 최근 개발한 제휴 상품 없는 경우의 일반 쿠팡 검색은 개인 구매와 승인된 업소 구매에서 조건에 맞게 제공된다. 승인된 특정 상품이 오래된 상태일 때는 이를 우회하지 않는다 (`coupang_purchase_planner.dart:122–128`; `business_coupang_page.dart:239–253`).
- 장보기 재료 없는 경우에는 준비 화면으로 이동하는 버튼이 있다 (`procurement_plan_page.dart:336–348`).
- AI 요청 제한 안내는 입력한 자막·힌트를 유지한다 (`youtube_recipe_enrichment_page.dart:609–611`). 외부 제한을 없애기보다 입력 보존과 재시도 경로를 유지한다.

## 공통 개선 설계

모든 화면에 관리 메뉴를 복제하는 것보다, 막힌 원인에 맞는 작은 해결 창이나 정확한 대상 화면을 여는 방식이 적절하다.

1. **원인 식별:** 빈 데이터, 검색 불일치, 입력 누락, 권한 부족, 승인 대기, 오래된 자료, 연결 실패를 구분한다. 실패 원인을 추측하여 일괄적으로 “인증·입력값 확인”으로 안내하지 않는다.
2. **해결 동작:** 각 원인에 등록·수정·재조회·로그인·승인 내역 확인 중 필요한 동작 하나를 우선 표시한다. 비활성 버튼 가까이에 이유를 둔다.
3. **초안 유지:** 현재 업소·계정·요청서·품목·버전·검색어·수량·단위를 유지한다. 인증정보는 초안에 넣지 않는다. 계정·업소가 바뀌면 다른 계정의 초안을 복원하지 않는다.
4. **결과 반영:** 새 항목 등록 결과를 반환받아 자동 선택하고 관련 목록을 갱신한다. 해결 창 취소 시 원래 입력을 보존한다. 완료 후 원래 버튼 위치로 돌아온다.
5. **최종 재검증:** 권한·승인·버전·잔량·환산을 서버에서 재검증하고 사용자가 다음 작업을 실행하게 한다. 재시도로 중복 요청·입고가 생기지 않도록 기존 중복 실행 방지 구조를 유지한다.

승인 대기, 소유자 전용 작업, 연습 공간의 실제 구매 제한, 외부 주문·환불, 이미 확정된 입고 매핑은 “불편함”만으로 제거하지 않는다. 사용자가 해결할 권한이 없으면 담당 절차와 현재 상태를 알려 주고, 강제 진행은 제공하지 않는다.

## 권장 구현 순서와 검증

### 1단계: 구매 준비와 입고 연결

공통 선택 창의 빈 상태·오류 재시도, 거래처·상품 즉시 등록, 입고 품목 등록 후 복귀, 잘못된 단위 안내부터 개선한다. 기존 등록 기능을 재사용할 수 있어 비교적 작은 변경으로 효과가 크다.

검증: 거래처 0개, 상품 0개, 검색 불일치, 비활성 상품, 조회 실패, 등록 취소·실패·중복, 저장 후 자동 선택, 입력량 유지, 계정·업소 전환, 등록 권한 없는 사용자.

### 2단계: 인증·승인·충돌 복구

로그인 복귀, 관리자 인증 복귀, 변경된 쿠팡 상품에서 요청서 수정 연결, 메뉴·레시피 선행 작업 연결, 중복 제휴 상품·편집 충돌 해결을 진행한다.

검증: 같은 계정 재인증과 다른 계정 로그인, 안전하지 않은 복귀 주소 거부, 인증 취소, 승인 권한 차이, 상품 비공개·수정, 동시 요청서 수정, 초안 보존, 재승인 전 구매 차단.

### 3단계: 재고 연결 환산과 정리 업무

재고 연결 단위 호환, 삭제·단위 변경의 연관 자료 탐색, 조리 완료 후 예약 정리를 진행한다. 특히 재고 연결 환산은 서버 규칙과 수량 계산에 영향을 주므로 별도 설계·새 마이그레이션·검증이 필요하다.

검증: g↔kg와 mL↔L, 개·봉·박스의 검증된 규격, 무게↔부피 자동 환산 금지, 소수 정밀도와 잔량, 중복 재고 방지, 예약 중 단위 변경, 부분 입고·반품, 동시 수정, 삭제 차단 사유 해결 후 영향 재조회.

공통 완료 기준은 **원인 파악 → 현재 위치에서 해결 시작 → 입력 보존 → 결과 반영 → 원래 업무 계속**이다. 웹과 Android의 공용 흐름뿐 아니라 뒤로 가기, 키보드, 외부 쿠팡 이동 후 복귀도 실제 기기에서 확인해야 한다.
