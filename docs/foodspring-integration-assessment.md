# 식봄 구매 연동 검토 및 실행 계획

검토일: 2026-09-26. 사용자는 식봄·마켓보로에 아직 문의하거나 제휴 승인을 받지 않았다고 확인했다.

## 결론

레시피 스카우트에서 구매할 품목을 준비하고 식봄에서 사용자가 직접 결제하는 흐름은 기존 외부 상품 링크 기능을 활용해 시범 운영할 수 있다. 다만 식봄의 상품 검색·가격·재고 조회, 장바구니 전달, 구매 주문 생성·조회용 공식 API 명세와 제3자 이용 승인은 공개 자료에서 확인하지 못했다. 현재는 API 연동 구현이나 운영 구매 성공을 선언할 단계가 아니다.

우선 업소 구매담당자 대상으로 식봄 결제 화면에 연결하는 방식을 협의하고, 허용된 구매 API 범위에 따라 자동화를 추가하는 것을 추천한다. 레시피 스카우트가 결제를 직접 처리하거나 판매자 주문관리 API를 구매 API로 전용하는 설계는 채택하지 않는다.

개인 구매요청서의 상품 링크 기능을 업소 공동 구매·식단의 API 주문 연결과 동일한 기능으로 설명하지 않는다. 공동 구매의 상품 매핑·권한·외부 주문 상태는 후속 구현 대상이다. 기존 제휴 상품 모듈은 쿠팡·네이버·유튜브용이므로 식봄을 임의로 해당 프로그램에 넣지 않는다.

## 지금 가능한 수동 시범 운영

1. 식봄에서 구매자가 직접 상품을 확인하고 해당 상품의 HTTPS 주소를 복사한다.
2. 레시피 스카우트의 개인 구매요청서 편집에서 **상품 링크로 업체 연결·품목 추가**를 선택한다.
3. 공개 업체에서 자동으로 찾지 못하면 상품 페이지의 실제 판매자를 확인해 거래처로 선택하거나 등록한다. 식봄 운영사를 실제 판매자로 추정하지 않는다.
4. 상품명·규격·판매 단위·구매 수량을 직접 확인해 저장한다. 예를 들어 필요한 양이 3kg이고 실제 상품이 2kg 봉지이면 구매 후보는 2봉지이며, 사용자가 확정한다.
5. 식봄 상품 페이지에서 배송 가능 지역·최소 주문·배송비·최종 금액을 확인한 후 식봄에서 직접 결제한다.
6. 레시피 스카우트의 구매 기록·입고 기록은 실제 주문과 입고를 확인해 수동으로 관리한다. 링크 열기나 요청서 저장은 주문·결제 완료가 아니다.

위 절차는 코드와 기존 문서로 확인한 수동 기능의 활용 안내다. 이번 검토에서 실제 식봄 계정 로그인·상품 결제·휴대폰 왕복 동작을 수행한 것은 아니다. 전용 식봄 버튼, 상품 검색 API, 장바구니 자동 입력, 자동 주문 동기화도 추가하지 않았다.

## 제휴 답변에 따른 구현 범위

| 식봄이 제공하는 범위 | 구현할 사용자 흐름 | 자동화하지 못하는 부분 |
| --- | --- | --- |
| 일반 상품 링크만 허용 | 구매 목록에서 사용자가 저장한 상품 페이지로 이동 | 가격·재고·장바구니·주문 상태 |
| 상품 데이터 API 또는 정식 피드 | 재료별 상품 후보와 규격·가격 기준 시각 표시, 사용자 선택 | 별도 장바구니 API가 없으면 자동 담기 불가 |
| 장바구니·결제 연결 API | 구매량·업소 배송지 조건 재확인 → 장바구니 전달 → 식봄에서 결제 | 결제 결과 API가 없으면 구매 완료 자동 판정 불가 |
| 구매 주문 조회 API·웹훅 | 주문번호와 품목 매핑, 배송·취소 상태 동기화 | 실제 입고 확인 전 조리 재고 반영 금지 |
| 판매자 API만 제공 | 이번 구매자 연동 요구를 충족하지 않음 | 별도 구매 제휴나 수동 상품 링크 방식 필요 |

## API 문서 수령 후 개발 순서

1. 계약 범위와 명세 확인: 구매자 인증 방식, API 주소·버전·권한, 테스트 환경, 호출 제한, 상품 데이터 이용 조건, 주문·취소·결제 책임을 확인한다.
2. 읽기 연동부터 검증: Supabase Edge Function에서 승인된 API를 호출한다. 비밀키는 서버 비밀 저장소에만 둔다. 앱·웹에 키를 넣거나 식봄 계정 비밀번호를 수집하지 않는다.
3. 상품 매핑: 업소 ID, 외부 판매자·상품·옵션 ID, 판매 단위와 내용량, 레시피 단위의 환산 기준을 연결한다. 가격·재고·지역·배송비는 API가 제공하는 범위와 기준 시각을 표시한다.
4. 구매 승인: 현재 업소 회원의 구매 권한을 서버에서 검사한다. 선택 품목·수량·배송지·최종 견적을 사용자가 확인한 뒤 장바구니 또는 주문을 전달한다. 가격 변경 시 재확인한다.
5. 중복 방지: 외부 요청 식별자와 응답을 보관한다. 응답이 끊긴 주문은 조회로 확인하기 전 새 주문으로 재전송하지 않는다. 식봄의 멱등성·조회 지원 여부에 맞춰 구현한다.
6. 주문 상태 연결: 문서에 정의된 주문번호·판매자별 분할 주문·부분 취소·환불 상태를 매핑한다. 웹훅 서명·중복·순서 역전을 검증하며, 지원하지 않는 기능은 표시하지 않는다.
7. 검증 후 배포: 승인된 테스트 환경에서 계정·업소 분리, 품절, 가격 변경, 배송 불가, 중복 클릭, 통신 실패, 취소, 모바일 결제 복귀를 확인한다. 실제 결제 테스트는 별도 확인 후 진행한다. 운영 반영 범위를 정해 DB·함수·웹·AAB를 배포한다.

API 미제공 시 숨겨진 API나 로그인 세션을 복제해 대체하지 않는다. 공식 문서와 계약이 도착하기 전에는 임의 엔드포인트·가상 상품·성공 응답을 운영 기능으로 만들지 않는다.
