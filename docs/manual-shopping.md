# Manual ingredients and reopening purchase preparation

The personal shopping preparation page offers **목록 수정·재료 추가** after confirmation, and **재료 직접 추가** while editing (including when no recipe list exists). Reopening clears only the device's preparation confirmation. It does not reopen purchased items, erase receipts or change stock.

The manual dialog accepts up to 100 ingredients per submission with explicit purchase quantities and units, plus optional package/brand specifications. Multiple ingredients can be queued before saving. An account-scoped device draft survives closing or external browsing. Ambiguous server responses lock the submission for an idempotent retry, including after restart. Credentials and account identifiers are never sent to stores.

The additive 0075 migration creates `create_manual_shopping_list(jsonb,uuid)` and an owner-scoped replay ledger. It creates a real active kitchen list with `source_recipe_id = null`, pending reviewed items and exact quantities. It never writes inventory or purchase records. Existing purchase/complete RPCs handle these items. Anonymous execution, managed input fields, invalid quantities/units and replay payload changes are rejected. Deleted lists retain a replay tombstone; stale retries cannot resurrect them.

`purchase_specification` defaults to an empty string for existing rows and is immutable after creation. Recipe API list/item responses expose it, with empty fallback. Different specifications remain separate in ordinary grouping and AI-assisted merging. Packaging units never receive an inferred weight or volume. If only ingredients are added on the same date with unchanged inventory, checks on unchanged groups are preserved; merged/changed groups need review and confirmation always resets. Removals, changed revisions, inventory changes or a new date invalidate the preparation.

Coupang exploration in the manual dialog displays existing published affiliate offers. An explicitly labeled ordinary Coupang search helps inspect other package sizes; it does not earn affiliate credit by itself or automatically import products. This does not re-enable the previously hidden ordinary search/Google/Naver buttons in the normal purchase dialog. Search uses only the user-entered ingredient and optional specification. No Coupang API key is required for this flow.

The hub continues to use the existing GoRouter preparation/active stages. A newly created manual list is selected along with the user's prior selection where safe. Business purchase requests keep their existing approval and permission model; their dedicated Coupang comparison flow is separate and does not write personal shopping records.

Validation: `tools/test/manual_shopping_contract.cjs` exercises the real kitchen migrations in isolated PGlite, including record/complete/replay/owner boundaries. Flutter tests cover reopening, exact units, specification grouping, durable drafts, account changes, duplicate taps, timeout retries, narrow screens and external search. Recipe API tests assert the new field without changing old response fields. Production application is additive, followed by deploying the backward-compatible recipe API, web build and Android version code 90 rebuild authorized by the user before Play upload.
