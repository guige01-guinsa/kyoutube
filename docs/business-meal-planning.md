# 업소별 식단 관리

## 사용 경로

업소·전문가 → 업소 선택 → 업무홈 → **식단 달력**. 공동 레시피 화면의 연결된 업무 도구에서도 열 수 있다. 경로는 `/business-workspaces/:workspace/meals`.

- 일간·주간·월간 보기, 날짜 이동, 오늘 돌아가기, 취소 기록 표시.
- 날짜·끼니(아침/점심/저녁/간식/직접 입력), 식단 이름, 메모를 작성한다.
- 공동 레시피 또는 판매 메뉴를 최대 20개 선택하고 **요리마다 준비 인분**을 정한다. 같은 요리를 다시 선택해 중복 등록할 수 없다.
- 레시피에 수량·단위가 있는 구조화 재료가 필요하다. 서버가 해당 업소의 레시피 버전에서 조리법과 재료량을 보관한다.
- 작성 중에는 수정·취소할 수 있다. 담당자가 확정하면 요리·인분을 직접 수정할 수 없다.
- 일간 또는 주간 보기에서 기간 복사, 주간 보기에서 지난주 복사. 새 날짜에 **작성 중** 상태로 복사하며 원본 레시피 버전을 유지한다. 같은 날짜·끼니가 있으면 전체 작업을 취소하므로 기존 식단을 덮어쓰지 않는다.
- 상세·이력에서 요리별 레시피 버전과 조리법, 합산 재료, 이전 식단 버전을 확인한다.
- 기존 `business_records.kind=meal` 기록은 공동 레시피 영역에서 그대로 조회·편집한다. 날짜·끼니·구조화 재료가 다른 과거 기록을 새 달력으로 자동 변환하지 않는다.

## 권한

| 업무 | 기존 권한 |
|---|---|
| 달력·식단 이력 조회 | recipes.read |
| 작성·수정·복사, 초안 취소, 조리 완료 | recipes.write |
| 식단 확정, 확정 식단 취소 | menus.approve |
| 구매 준비 | recipes.read + purchasing.read + purchasing.write |

업소 소유자는 기존 소유자 권한을 따른다. 결제·직원 활성 상태는 기존 `business_can`에서 검사한다. 직원 메뉴의 메뉴 승인 권한 설명에 식단 확정을 포함했다.

## 구매 연결

1. 확정한 식단을 기간 안에서 최대 20개 선택한다.
2. **선택 식단 구매 준비**에서 납품일을 정하고 재료·구매량을 계산한다.
3. 재료별 기본 구매처·상품·포장·단위 환산과 연결 재고를 확인한다. 같은 이름·규격·단위의 재료만 합산한다.
4. 진행 중 구매요청 중복 안내를 검토한다. 입고 예정량은 자동 차감하지 않는다.
5. 사용자 확인 후 업체별 **구매요청서 초안**을 만들고 선택한 재고를 예약한다. 주문 전송이나 승인 완료는 자동 수행하지 않는다.
6. 달력의 **구매 준비 내역**에서 생성된 요청서와 재고 관리로 이동한다.

확정 식단과 구매 배치를 연결해 다른 토큰으로도 같은 식단을 두 번 구매 준비할 수 없도록 한다. 응답이 끊기면 같은 토큰으로 결과를 재확인한다. 이미 구매 준비한 식단은 취소하지 못한다. 요청서 자체의 수정·취소 및 미사용 예약 해제는 기존 구매·재고 흐름에서 처리한다. 같은 식단을 취소 후 재구매하는 자동 재개 흐름은 제공하지 않는다.

**조리 완료는 식단 상태만 변경한다.** 실제 사용·손실량은 재고 관리에서 기록한다. 임의의 재고 차감이나 단위 환산을 하지 않는다.

## 구현 및 배포

새 마이그레이션: `supabase/migrations/0072_business_meal_planning.sql`.

- business_meal_plans: 업소·날짜별 자료와 서버에서 만든 레시피/필요량 스냅샷.
- business_meal_history: 변경 버전별 보관. 직원 직접 쓰기·삭제 불가.
- business_meal_copies: 복사 요청 재시도 식별.
- business_meal_purchase_links: 식단의 최초 구매 배치 연결.
- 기존 메뉴 구매 RPC는 비식단 입력에서 이전 동작을 유지한다. 식단은 원자적인 배치 생성 경로만 허용한다.
- 작업은 업소 행 잠금으로 직렬화하고 revision으로 동시 수정을 검출한다. 타 업소 자료·원본 조리법을 클라이언트가 주입할 수 없다.

2026-09-25 후속 사용자 승인으로 **운영 DB0072 적용·웹 v84 배포·서명 AAB84 생성 완료**. 운영 RLS·RPC·이력 및 인덱스 후검증을 통과했다. 0071 이하 마이그레이션과 기존 누락 이력은 변경하지 않았다. Play v84 업로드·휴대폰 업데이트는 아직 수행하지 않았다. [릴리스 검증 및 제한](release-v84.md).

## 검증

- `node tools/test/business_workspaces_contract.cjs --meals`: 실제 SQL을 격리 PGlite PostgreSQL에서 실행. 기존 구매 회귀검사 포함 280개 통과, 운영 쓰기 0.
- `test/features/business/business_meal_test.dart`: 날짜 경계, 모바일 확대 글자, 작성·복사 응답 재시도, 직원별 확정 권한, 구매 연결, 중복 선택 차단, PC/영문 화면.
- 로컬 Supabase Docker 재검증은 `Local Supabase status is unavailable`로 실행하지 못했다. Docker/실제 운영 DB 검증으로 간주하지 않는다.
- `flutter doctor -v`는 고정 SDK를 사용했으나 기존 PATH의 전역 Flutter/Dart, Android 라이선스 상태 미확인, Windows Visual Studio 설치 불완전 경고를 표시했다. 초기 기능 작업에서는 Android 릴리스 빌드를 실행하지 않았으나, 후속 v84 배포에서 지정 SDK/JDK17의 서명 AAB 빌드가 성공했다.
- 전체 Flutter 검증 결과는 CURRENT_STATUS.md 참조.

후속 확장: 식단별 원가·실제 소비·잔반 비교, 인쇄/PDF, 영양·알레르기 검토. 현재 기능에서 자동 영양 판정은 하지 않는다.
