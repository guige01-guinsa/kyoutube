## 백업과 복구 검증의 정확한 범위

운영 함수 9개와 public 스키마/업무 데이터 백업을 `.local-backups/security-20260913/`에 보관했다. 별도 로컬 DB `recipe_scout_restore_20260913`에 실제 복원한 결과 업무 테이블 35개, 레시피 31건, 작업실 2건, 버전 2건을 확인했다. 복원 명령 소요는 약 6.2초이며 운영 장애 복구시간 보장은 아니다.

위 첫 public 전용 시험은 auth 대체 구조를 사용했다. 이후 사용자가 비밀번호 해시·세션 토큰을 포함한 암호화 백업을 명시적으로 승인하여 아래 추가 시험을 완료했다. 운영 API는 PITR 비활성 및 열람 가능한 물리 백업 목록 없음으로 응답했다. 업로드 이미지 실물은 당시 0건이었다. 앞으로 파일이 쌓이면 DB와 별도로 스토리지 파일 백업도 필요하다.

추가 암호화 백업은 `.local-backups/encrypted-recovery-20260913T044450Z/recipe-scout-recovery.encrypted.json`에 보관했다. `public`, `auth`, `storage`, `supabase_migrations`의 실제 스키마/데이터를 메모리에서 수집해 AES-256-GCM으로 암호화하고, 키는 현재 Windows 사용자 DPAPI로 보호했다. 이 작업은 평문 SQL 파일을 만들지 않았다. 파일 크기는 435,576바이트, SHA-256은 `476d25c0fb12a2c79ec963637c2a523a5fe30aa05bc26ceb45ae33b2ee0c51f5`이다. 복호화·내부 해시·변조 거부 검사를 통과했다.

외부 네트워크/포트/컨테이너 로그가 없는 별도 PostgreSQL 17.6 임시 컨테이너의 tmpfs에 실제 복원했다. **66개 테이블, 2,907개 행 전체가 원본 COPY 데이터와 일치**했다. 사용자 23명, 세션 56개, 갱신 토큰 97개, 레시피 31건, 작업실 2건, 버전 2건을 포함한다. 인증 데이터 값은 출력하지 않았다. 복원·대조는 약 38.4초였으며 시험 컨테이너 제거도 확인했다.

현재 Windows 계정의 DPAPI 복호화 환경이 필요하므로 파일만 다른 PC에 복사하는 방식의 복구는 보장되지 않는다. 로그인/OAuth/메일/갱신 흐름 자체, Supabase 프로젝트 서명·암호화 비밀, 스토리지 파일 본체는 이번 DB 복원 시험에 포함하지 않았다. 실행 및 보관 절차는 [암호화 복구 백업](encrypted-recovery-backup.md)에 기록했다.

이 로컬 백업만으로 오프사이트 재해 복구나 자동 일일 백업이 마련되었다고 볼 수 없다. 운영 시작 기준으로 권장하는 목표는 RPO 24시간/RTO 4시간이며, 실제 공급자 백업과 격리 복원 훈련을 갖춘 후 확정해야 한다. 관리자 계정 복구는 본인 확인 → 프로젝트 콘솔에서 해당 팩터만 초기화 → 본인 재등록 순서로 수행하고 기록한다. 인증 비밀키 공유로 복구를 대신하지 않는다.

## 후속 반영 순서

1. 열어 둔 Google 로그인 화면에서 관리자가 로그인한다. Play 테스트 트랙으로 v59 AAB를 배포한 뒤 휴대폰에서 업데이트하고 핵심 화면을 확인한다.
2. 관리자 본인이 인증 앱에 TOTP를 등록한다. 등록 및 AAL2 접근을 확인한 뒤 이미 승인된 보안 범위의 0047·0048을 순서대로 적용한다.
3. Google 관리자 연결을 복구해 결제/FCM 서버 인증을 구성한다. 실제 테스트 구매·푸시 수신을 확인한 후 완료로 기록한다.
4. 지원 플랜의 유출 비밀번호 보호와 외부 재해 복구 백업/키 관리 방식을 확정한다. 승인된 인증 포함 로컬 암호화 백업 및 DB 복원 시험은 완료했다.

Google 접속과 본인 TOTP 등록은 작업 권한과 별개로 필요한 외부 조건이다. 민감 인증 데이터 백업은 추가 승인을 받아 완료했다. 나머지 승인된 DB·함수·자료 보호 작업은 완료했다.
