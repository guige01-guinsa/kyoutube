# 요리사 일정관리와 레시피 스카우트 개발 계획

2026년 10월 10일 기준 개발 설계 1.1. 앱의 최초 출시 범위는 1.0이며 문서 개정 번호와 구분한다.

독립된 요리사 일정관리 앱을 출시하고 레시피 스카우트와 서로 필요한 기능을 연결한다. 기존 진화형 업무별 일정관리 시스템은 원본 프로젝트와 운영 환경을 유지한다. 새 앱은 하루의 준비 순서와 실행을 관리하면서 업무별 레시피 스카우트 사용 가이드 역할을 맡는다. 레시피 스카우트는 레시피·식단·재료·구매·원가와 공통 사용법의 기준 자료를 관리한다. 승인한 공통 가이드는 영상홍보 시스템의 제작 자료로도 활용한다.

새 앱의 작업명은 **요리사 일정관리**다. 실제 앱 이름, 상표, GitHub 저장소, 설치 식별자와 도메인은 개발 착수 단계에서 확정한다. 아래 설계의 기능은 개발 대상이며 현재 출시된 기능을 뜻하지 않는다.

## 제품 목표와 사용 대상

첫 대상은 소규모 음식점 사장과 조리 담당자다. 직원 공동 배정은 후속 버전으로 분리하고, 첫 버전에서는 한 사람이 업무를 계획하고 완료하는 흐름을 완성한다.

사용자는 영업 시작이나 제공 시간을 입력하고 템플릿을 선택한다. 앱은 구매 확인, 손질, 준비, 제공, 마감 작업을 시간순으로 제안한다. 사용자가 수정·확정한 일정에만 알림을 예약하고, 완료·미완료와 실제 걸린 시간을 기록한다. 반복 기록에서 개선안을 제안하며 사용자가 다음 템플릿에 반영할지 선택한다.

첫 사용 목표는 가입 없이 5분 이내에 첫 업무 일정을 만드는 것이다. 이 시간은 사용자 시험의 목표이며 측정 결과가 아니다.

레시피 스카우트에는 이미 업소 식단 달력과 공동 구매 기능이 있다. 새 앱의 달력은 업무 실행을 관리한다. 식단 제공일이 바뀌면 관련 일정 변경안을 보여 주고 사용자가 적용한다. 조리 업무 완료만으로 식단 확정, 구매 승인, 입고, 재고 차감이나 매출 기록을 처리하지 않는다.

## 원본 시스템을 보호하는 개발 방식

기존 일정관리 시스템은 `https://ai-schedule-three.vercel.app/`, 원본 저장소는 [guige01-guinsa/ai-schedule](https://github.com/guige01-guinsa/ai-schedule)다. 기준 커밋은 `19879b6aeffe7c10f4e636f26bf7075fbcbd96f3`, 최신 개발 시각은 **2026년 10월 9일 15:36:34 한국 시간**이다. Next.js·Supabase와 직무별 반복·추천·실행 소스를 확인했다. 원본에는 식당 구매 담당자용 8개 모듈·16개 템플릿이 있으며 구매·재고·납품 등의 확인 항목에 활용한다. 로그인한 운영 화면과 DB 적용 상태는 착수 검수에서 대조한다.

1. 원본 저장소의 정확한 커밋을 기록하고 재사용 가능한 일정·반복·템플릿 로직과 라이선스를 점검한다.
2. 새 저장소에 필요한 코드만 가져오고 원본 출처와 커밋을 기록한다. 환경 파일, 사용자 자료, 서비스 키, 배포 설정과 앱 서명키는 복사하지 않는다.
3. 새 앱에는 별도 개발·시험·운영 환경과 DB, Firebase 프로젝트, 배포 경로를 사용한다.
4. 원본 일정관리의 기존 업무·일정 기능과 배포 흐름을 유지한다. 사용자 요청에 따라 회원 연결과 식당 업무의 선택형 가이드만 별도 변경으로 검토한다. 원본 main push는 Vercel 배포로 이어질 수 있으므로 새 앱 개발을 원본에 넣지 않는다. 이후 공동 모듈 추출은 두 프로젝트에서 별도로 검토한다.
5. 레시피 스카우트에는 검토한 연결 화면과 필요한 연동 API만 추가한다. 기존 레시피·회원권·구매 권한을 유지한다. 회원 연결은 무료 이용권 등록이며 고급 원가·업소 권한을 자동 부여하지 않는다.

새 저장소나 클라우드 자원은 이 계획으로 생성하지 않았다. 앱 패키지 이름과 운영 도메인은 확보 여부를 확인한 뒤 결정한다.

## 무료회원과 공동 로그인

기존 일정관리와 새 요리사 앱의 회원 모두에게 레시피 스카우트 무료회원 이용 경로를 제공한다. 가입 또는 최초 연결 화면에서 이용약관과 필요한 정보 전달에 동의하면, 처음 레시피 스카우트로 이동할 때 별도 가입 양식 없이 무료회원 이용 등록을 완료한다. 각 서비스의 자료와 회원권은 분리하고 비공개 업무 자료 연결은 별도 동의를 받는다.

이미 레시피 스카우트 회원인 사용자는 기존 계정에 로그인해 연결한다. 유료 회원을 무료로 낮추거나 기존 레시피·업소·구매 자료를 덮어쓰지 않는다. 공동 로그인은 별도 비밀번호를 기억해야 하는 부담을 줄이지만 최초 인증과 동의를 생략한다는 뜻은 아니다.

회원 연결의 자세한 흐름은 [회원 설계](MEMBERSHIP_KO.md)에 있다. 원본의 Supabase 이메일·Google·카카오 로그인은 확인됐다. 다른 앱에 공동 로그인을 제공하는 설정은 시험이 필요하며 필요한 최소 인증 변경은 업무 기능 변경과 분리한다.

| 업무 가이드 | 해야 할 일·확인 항목·사용법·다음 행동 | 기존 가이드 열기, 직접 확인과 원본 확인 구분 |
| 개선 제안 | 기록 수, 기존 시간, 제안 시간, 적용 범위 | 다음 일정부터 적용, 보류, 되돌리기 |
| 계정과 연결 | 백업 상태, 연결 앱, 알림, 삭제, 도움말 | 계정 전환 시 캐시 분리, 연결 해제 범위 설명 |

빈 화면에서는 샘플 템플릿을 제안한다. 알림을 허용하지 않아도 일정과 완료 기능은 사용할 수 있게 한다. 연결 앱이 없어도 웹 안내와 설치 선택을 제공한다.

## 대표 사용 흐름

### 레시피에서 준비 일정 만들기

사용자가 레시피 스카우트에서 요리를 고르고 ‘조리 일정 만들기’를 누른다. 최초 버전은 요리사 일정관리의 공개 템플릿 안내로 이동하며, 사용자는 제공일·시간과 업무를 확인해서 일정을 만든다. 비공개 자료를 전달하는 후속 버전에서는 자료 연결 동의를 받고 한 번만 처리되는 전달 절차를 사용한다. 생성은 항상 미리보기와 사용자 확정으로 끝난다.

### 일정에서 준비 내용 확인하기

‘금요일 점심 준비’의 조리 업무에서 ‘레시피 스카우트에서 준비하기’를 누른다. 첫 버전은 해당 기능의 안내 또는 검증된 앱 진입 경로로 이동한다. 후속 버전에서는 연결한 레시피와 버전을 권한 확인 후 연다. 돌아오면 원래 업무 상세로 복귀한다. 링크를 열었다는 사실만으로 업무를 완료하지 않는다.

### 기록을 다음 계획에 반영하기

같은 업무의 유효한 실제 시간 기록이 5개 이상이면 개인별 최근 20개 기록의 중앙값을 기준으로 제안을 만든다. 예상 25분, 기록 중앙값 35분이면 20퍼센트 상한에 따라 첫 제안은 30분이다. 근거 중앙값과 적용값을 함께 보여 주고 사용자가 승인한 템플릿의 새 버전을 다음 생성부터 사용한다. 이미 진행 중인 일정은 유지한다.

## 양방향 홍보와 측정

홍보는 관련 업무에서 다음 준비 행동을 돕는 버튼으로 제공한다. 첫 실행 전체 화면 광고와 업무 알림에 홍보 문구를 넣는 방식은 범위에 포함하지 않는다. 두 앱의 기본 기능은 상대 앱 설치 없이 사용할 수 있다.

| 출발 위치 | 버튼 | 도착과 성공 기준 |
|---|---|---|
| 레시피 상세 | 조리 일정 만들기 | 템플릿 적용 후 첫 일정 확정 |
| 업소 식단 | 준비 업무 일정 만들기 | 선택 식단의 준비 업무 생성 |
| 요리사 업무 상세 | 레시피 찾아보기 | 레시피 검색·열람 |
| 구매 준비 업무 | 레시피 스카우트에서 구매 준비 | 원본 구매 준비 화면의 실제 사용 |
| 원가 검토 업무 | 원가 확인하기 | 권한이 있는 원본 원가 기능 사용 |

최초 연결은 지원 범위를 표시하고 실제 도착을 검증한다. 고급 원가·업소 기능에는 기존 레시피 스카우트 이용권과 권한을 적용하며 무료 제공으로 오해할 문구를 쓰지 않는다.

동의한 사용자만 출발 앱, 버튼 위치, 템플릿 종류, 캠페인, 도착과 첫 유효 행동을 측정한다. 클릭과 설치·가입을 같은 지표로 계산하지 않는다. 설치 후 원래 링크로 돌아오지 않은 이용자는 자동으로 이어졌다고 집계하지 않는다. 상세 기준은 데이터 설계 문서에 있다.

## 기술 선택과 원본 재사용

새 앱의 기본안은 Flutter와 Riverpod 및 go_router, 독립 Supabase, Android 알림과 로컬 저장이다. 기존 레시피 스카우트와 개발 경험을 공유하며 Android 앱·태블릿·웹으로 확장한다. 웹은 초기 시험과 연결 안내용이며 Android와 알림·오프라인 지원 범위를 동일하게 약속하지 않는다.

원본은 Next.js·TypeScript이며 새 앱의 화면은 Flutter로 만든다. 순수 날짜·회차·추천 규칙은 Dart와 서버 TypeScript로 이식하고 같은 검수 입력으로 비교한다. Node·Next.js·관리자 DB 코드는 제외하고 독립 Supabase Edge Functions와 원자 저장 RPC로 재작성한다. 새벽·야간 영업, 사용자 승인, 계정별 오프라인 저장과 모바일 알림은 새 앱에서 구현한다. 구체적인 재사용 파일과 원본과의 차이는 [소스 검토](SOURCE_REVIEW_KO.md)에 있다.

AI 없이도 일정과 개선 제안이 동작하게 만든다. 초기에 반복 사용 기록과 사용자의 수정으로 템플릿이 개선되며, AI는 후속 선택 기능으로 둔다.

## 개발 일정과 자원

아래는 소스 확보 후 숙련 개발자 1명과 필요할 때의 디자인·시험 지원을 가정한 계획 범위다. 확정 납기나 실제 견적이 아니다. 단계는 완료 조건을 통과한 뒤 진행한다.

| 단계 | 계획 기간 | 완료 결과 |
|---|---|---|
| 분리와 인증 시험 | 1~2주 | 확인한 소스 기준으로 새 환경, 날짜 규칙 이식, 공동 로그인 POC |
| 화면과 일정 기본 구현 | 2주 | 체험, 오늘·주간 화면, 6개 템플릿, 일정 생성 |
| 반복과 알림 및 동기화 | 2~3주 | 반복 예외, 오프라인 저장, 충돌 처리, 알림 상태 |
| 개선 제안과 가이드 및 양방향 연결 | 1~2주 | 템플릿 버전, 시간 제안, 업무 안내, 링크·도착 검증 |
| 실제 사용자 시험 | 2주 | 소규모 업소 5~10명의 업무 시험과 수정 |
| 출시 준비와 회귀 확인 | 1~2주 | 내부 시험 앱, 삭제 경로, 스토어 자료, 승인된 배포 |

최초 공개까지 약 9~13주를 기본 범위로 보고 재작업 여유를 포함한 일정은 10~14주로 잡는다. 두 앱의 비공개 자료 연동은 별도 3~5주, 가이드의 24초 영상 제작 연계는 별도 2~3주, 직원 공동 업무는 별도 4~6주를 우선 추정한다. 음성·화면 영상은 추가 3~5주를 별도 산정한다. 로그인 POC와 실제 샘플 결과로 조정하며 한 사람이 모두 맡으면 기간을 합산한다. 앱 심사와 계정별 출시 조건은 별도다.

개발 주담당은 앱·서버·연동·검증 작업을 수행한다. 제품 책임자는 템플릿 업무 내용과 출시 범위를 결정하고 실제 요리사 시험 참여자를 확보한다. 디자인 지원은 첫 화면과 조작성을 점검하며 시험 지원은 실제 기기·권한·날짜 경계와 업소 격리를 확인한다.

## 출시 판정

첫 앱 일정은 사전 미리보기와 사용자 확정으로만 생성한다. 반복 생성 재시도, 다른 기기의 동시 수정, 날짜 변경과 알림 해제에서도 업무·알림이 중복되거나 조용히 덮어써지면 출시하지 않는다.

사용자 시험의 목표는 첫 일정 생성 중앙값 5분 이내, 참여자 80퍼센트 이상이 도움 없이 핵심 흐름 완료, 일정 손실과 타 사용자 자료 노출 0건이다. 앱 안정성 목표는 시험 관측 기준 오류 없이 끝난 세션 99.5퍼센트 이상이다. 참여자가 적으면 백분율과 함께 실제 인원·세션 수를 보고한다.

양방향 홍보는 도착 확인과 첫 유효 행동을 구분해 측정한다. 첫 4주에는 전환율과 주간 재방문을 관측해 기준을 만들고, 성과를 보장하는 수치나 수익 예상으로 바꾸지 않는다.

## 출시 이후 확장 순서

1. 운영 기록을 바탕으로 기본 템플릿과 알림을 개선한다.
2. 승인한 업무 가이드를 영상홍보 제작 자료로 연결하고 비공개 샘플을 검수한다.
3. 명시적 동의를 받은 비공개 레시피·식단 연결과 원본 변경 알림을 추가한다.
4. 직원 배정·주방별 업무량·업소 권한을 추가한다.
5. 실제 사용 필요가 확인된 경우 음성·화면 영상, AI 초안과 유료 팀 기능을 검토한다.
