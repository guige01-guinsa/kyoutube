# 관리 기능 CRUD 검토

2026-09-30. 현재 작업 소스의 화면, 저장 경로, DB 마이그레이션과 관련 테스트 코드를 점검한 설계 의견이다. 이번 검토에서는 제품 코드, 운영 DB, 웹, v90 AAB를 변경하지 않았고 테스트를 새로 실행하지 않았다. 운영 계정의 실제 데이터나 사용자별 화면을 직접 조작한 점검은 아니다.

## 결론

추가·조회·수정·삭제의 접근 방식을 통일하면 관리가 쉬워진다. 다만 삭제 동작은 자료의 성격에 따라 달라야 한다. 거래처·상품 같은 기준 정보와 구매요청·입고·매출 같은 거래 기록을 같은 방식으로 영구 삭제하면 안 된다.

권장 기본값은 수정 / 복제 / 사용 중지 / 보관 / 복원이며, 영구 삭제는 사용 이력이 없고 다른 자료가 참조하지 않는 항목에 한정한다. 기존에 있는 보관·복원과 권한·수정 충돌 검사 기능을 재사용하는 편이 안전하다. 안전한 구현이 가능한 범위와 추가 검증이 필요한 범위를 나누어 진행한다.

## 우선 보완할 근거

### 1. 개인 구매요청의 영구 삭제 범위가 넓다

`supplier_requests_page.dart`의 요청서 미리보기는 상태와 관계없이 삭제 버튼을 표시한다. `supplier_request_repository.dart`는 소유자와 ID로 직접 DELETE한다. 0052의 삭제 정책도 소유자 조건만 확인한다.

0061의 `supplier_request_events`는 요청서 삭제 시 함께 삭제되고, 0059의 연결 평가도 요청서 삭제 시 제거된다. 실제 구매·재고를 되돌리는 동작이 아니므로 요청서와 처리 근거만 사라질 수 있다. 사용자 확인창에 경고는 있으나, 완료 기록 관리의 기본 동작으로는 보관이 적합하다.

화면 버튼만 변경하면 구형 Android 클라이언트나 직접 API 호출이 기존 삭제 경로를 계속 사용할 수 있다. 구현 시 새 마이그레이션에서 삭제 정책과 관련 쓰기 경로를 함께 제한하고, 구형 앱에는 안전한 거절 응답을 제공해야 한다. 계정 탈퇴 전체 삭제는 별도 절차로 유지한다.

### 2. 저장한 구매 계획의 관리 경로가 부족하다

`business_menu_fast_repository.dart`는 저장 시 revision 0을 전달하고, 화면은 새 ID를 만든다. 서버의 `business_menu_template_save`에는 기존 ID/revision으로 갱신하는 기능이 있다. 현재 화면에는 기존 계획의 이름/구성 수정·보관 경로가 연결되지 않았다.

계획은 업소당 100개 제한이 있어 계속 새로 저장하는 방식은 정리 기능이 필요하다. 화면의 기존 자료 수정 경로와 보관/복원, 사용량 안내를 먼저 보완할 가치가 높다. 보관한다고 물리적 저장량이 줄어드는 것은 아니므로 제한 계산 방식도 명시적으로 결정해야 한다.

### 3. 사용 중지·보관·취소는 서로 다른 작업이다

- 사용 중지: 앞으로 구매 후보나 판매 대상에 사용하지 않는다. 과거 거래 사본은 유지한다.
- 보관: 기본 목록에서 숨기고 복원할 수 있다. 재고·금액 집계와 업무 상태는 바꾸지 않는다.
- 거래 취소/정정: 업무 상태나 집계에 영향을 주므로 사유와 이력이 필요하다. 외부 업체에 자동 통보하지 않는다.

특히 업소 매출의 기존 사용 중지는 매출 집계에서 제외되지만, 구매 기록 보관은 집계를 유지한다. 버튼을 같은 이름으로 단순 통합하면 안 된다.

## 화면 설계 제안

메뉴를 더 늘리기보다 현재 목록과 상세 화면에 공통 관리 메뉴를 둔다.

1. 상단: 검색, 사용 중/중지/보관함 필터, 새로 추가.
2. 행 또는 카드: 상세 보기와 `더보기` 메뉴. 수정·복제·중지·보관·복원 중 권한과 상태에 맞는 작업 표시.
3. 처리 불가 시 이유 표시: 예를 들어 “진행 중 구매요청이 있어 삭제할 수 없습니다. 사용 중지를 이용하세요.”
4. 여러 항목 선택은 보관/중지부터 제공. 선택한 개수와 영향을 미리 보여주고 서버가 전체 대상을 다시 검사.
5. 보관함에서 원래 화면으로 복원. 복원은 재주문·재입고·재공개를 의미하지 않음.

개인 거래처, 업소 공동 거래처, 공급업체 공개 카탈로그는 소유권과 공개 범위가 다르므로 데이터를 합치지 않는다. 조작 방식만 통일하고 현재 공간/공유 범위를 명확히 보여준다.

## 안전 조건과 제외할 작업

- 계정·업소·역할을 서버에서 확인하고 수정 번호와 연결 자료를 같은 트랜잭션에서 재검사한다.
- 저장/삭제/복원 재시도에도 요청서·입고·재고가 중복 생성되지 않아야 한다. 삭제 때문에 기존 재시도 기록을 지워 중복 처리를 허용하지 않는다.
- 업체/상품 원본 수정은 이전 구매요청의 거래 당시 사본·규격·환산 계수를 바꾸지 않는다.
- 입고 내역의 수량/단위 덮어쓰기, 승인/전달 기록 영구 삭제, 참조 자료 연쇄 삭제는 공통 CRUD 대상에서 제외한다.
- 재고 품목의 g↔kg 변경도 기존 수불과 예약을 함께 검증해야 한다. “봉”을 무게로 추정하거나 품목명을 기준으로 자동 병합하지 않는다.
- 현재고·예약·미완료 발주·기본 구매 설정 등 참조가 남은 항목의 삭제는 거절한다. 단순히 현재고가 0이라는 이유만으로 삭제하지 않는다.
- 중지/보관된 자료도 등록 한도에 포함되는 현재 구조가 있으므로 임의 영구 삭제로 해결하지 않고 한도와 보존 정책을 함께 설계한다.

## 권장 적용 순서

1. **기존 기능의 접근성 통일:** 거래처/상품 상태 변경, 요청서 상세의 보관·복원, 상태·권한에 따른 관리 메뉴와 안내.
2. **누락된 관리 보완:** 저장한 구매 계획 수정·복제·보관, 미사용 자료만 삭제 가능 여부 확인, 개인 요청서의 거래 이력 보호.
3. **별도 정정 설계:** 입고/재고/원가/매출의 정정 사유·상쇄 기록·복원 조건. 일반 삭제 메뉴에 섞지 않음.

구현 후에는 타 계정/업소 접근, 읽기 전용 직원, 변경 충돌, 구형 앱의 삭제 호출, 참조 중 삭제, 재시도, 단위 변경, 부분 입고/반품, 보관 전후 집계 동일성과 복원, 공개상품 복원 후 비공개 유지를 검사해야 한다. Flutter 필수 검증과 격리 DB 검증을 통과한 범위만 배포 대상으로 삼는다.
