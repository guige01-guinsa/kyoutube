## 반영 내용

- **업소 공동 업무 → 공동 레시피**에서 구매 기준 재료의 품명·규격·조리량·단위를 입력하고 기준 인분을 정합니다.
- 시험 조리 결과 → 경영 담당자/사장의 출시 승인 → **메뉴판 관리**에서 승인 버전·판매가·출시 준비/판매 중/판매 중지를 관리합니다. 메뉴판은 로그인한 업소 직원의 내부 미리보기입니다.
- **메뉴·레시피에서 구매**에서 개발용/출시 준비용/영업용 목적에 맞는 레시피 또는 판매 메뉴를 먼저 선택하고 인분을 입력합니다.
- 서버가 재료 필요량을 계산하며 담당자가 사용 가능한 재고·입고 예정량·포장 규격을 확인합니다. 업체별 필요한 재료를 골라 기존 구매요청 편집기로 이어지는 초안을 만듭니다. 자동 발주·재고 차감은 하지 않습니다.
- 메뉴는 승인된 레시피 버전에 고정됩니다. 이후 개발 변경이 판매 배합이나 과거 구매 기준을 덮어쓰지 않으며 버전 비교와 변경 이력을 제공합니다.
- 별도 AI 호출·유료 외부 API를 추가하지 않았습니다. 기존 Business 이용권·직원 권한·구매 승인 절차를 유지합니다.

## 운영 DB

- 프로젝트 `dfczeudklykypysiseck`에 **0067만** 적용했습니다. 기존 보류 0064는 적용하지 않았습니다.
- 기존 함수 정의·ACL·마이그레이션 이력을 사전 보관하고, 이력/함수 지문을 확인한 뒤 하나의 트랜잭션으로 적용했습니다. 개인·업소 자료를 덤프하거나 업무 행을 변경하는 마이그레이션은 아닙니다.
- 새 4개 테이블의 RLS, 회원 SELECT, 직접 쓰기·익명 접근 차단, RPC의 고정 search_path, 외래 키, 기존 권한·이용권 함수 보존을 확인했습니다.
- 기존 검증/저장/중지 함수는 외부 실행이 차단된 내부 함수로 보존했습니다. 변경 전 업소/직원/레코드/버전 수는 변경 직후와 같았습니다.
- 실제 PostgreSQL의 독립 DB **158개 통과**, PGlite **158개 통과**. Docker 검사에서 드러난 테스트 드라이버의 SQL 배열/JSON 배열 차이를 테스트 도우미에서 명시적으로 처리했습니다. 제품 코드 변경은 없었습니다.
- 운영 DB에서 가상 자료를 사용하는 **21개 검사**를 실행하고 전체 트랜잭션을 롤백했습니다. 출시 승인·버전 보존·재료 환산·포장 올림·초안 상태·중복 생성 방지·권한·RLS·판매 중지·기준 이력 보존을 확인했습니다. 테스트 사용자/업소/레코드/메뉴 잔여 0건, 메일·AI·결제 호출 0건. 검증 중 identity 시퀀스 번호에 빈 구간이 생길 수 있습니다.
- 실제 REST 요청에서 새 4개 테이블의 익명 읽기와 4개 RPC의 익명 실행은 모두 HTTP 401로 차단됩니다. Edge Function 배포·비밀키·프로젝트 설정 변경은 없습니다.
