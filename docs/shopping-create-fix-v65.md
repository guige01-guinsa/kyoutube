# 장보기 준비·목록 생성 수정 — v65

상태: 2026-09-15 사용자 승인으로 **운영 DB 0058 적용·v65 서명 AAB 생성과 검증 완료**. 휴대폰 설치는 사용자가 직접 진행한다. [배포 기록](release-v65.md)을 참고한다.

## 확정한 제품 원칙

- **조리 수량·단위**는 사용자가 레시피에서 관리한다. 인분 계산은 셰프 기능에서 수행하며, 장보기에서는 조리량을 자동 구매량으로 사용하지 않는다.
- **구매 수량·단위와 구매 이력**은 장보기에서 별도로 관리한다. 구매량 변경은 조리 원문이나 과거 구매 기록을 덮어쓰지 않는다.
- 구매 단위의 kg↔g, L↔mL, dozen↔개는 표준 기준으로 환산한다. 상품별 포장·밀도 등 기준이 없으면 임의 환산하지 않는다. 장보기 준비 편집창에서 `기존 1단위당 새 단위 수량`을 입력하거나 최종 구매량을 직접 입력한다. 예: 2팩, 1팩=300g → 600g → 0.6kg. 직접 입력한 환산 기준은 이번 편집 계산에 사용하고 결과 구매량을 저장하며, 전역 단위 규칙으로 자동 등록하지 않는다.
- 작은술·큰술·컵은 새 구매 입력의 선택지에서 제외한다. 기존 기록을 읽거나 셰프의 조리 단위를 사용하는 기능은 유지한다.
- **조리 완료 기록은 재고를 차감하지 않는다.** 현재 서버가 이미 조리 이력만 저장하는 것을 확인했으며, 재고 및 장보기 기록이 바뀌지 않는 회귀 검증과 안내를 추가했다. 보유량은 실제 수량을 직접 확인하는 참고값이다.
- 조리에 따른 잔량을 추적하지 않으므로 과거 보유 기록만으로 장보기 재료를 자동 제외하지 않는다. 새 준비 목록은 전체 선택으로 시작하고 사용자가 실제 보유 재료를 제외한다.

## 확인한 원인

1. 레시피 ID별로 보관한 장보기 검토 초안이 현재 재료와 비교되지 않아, 레시피에서 밥 120g·달걀 1개로 저장한 뒤에도 이전 `[확인 필요]` 문구와 빈 수량이 표시됐다.
2. 앱과 Edge API, DB 검토·구매 완료 함수는 37종 단위를 지원하지만, 목록 생성 RPC는 0018의 g/kg/ml/l/ea 검사를 유지했다. 0029에서는 생성 RPC 변경이 누락됐다. 작은술(tsp)·큰술(tbsp)이 하나라도 포함되면 전체 생성 트랜잭션이 실패하므로 밥·달걀을 제외해도 해결되지 않았다.
3. 수량 파서가 `½ 개`를 인식하지 못했다. 또한 클라이언트 오류 파서는 실제 서버의 `details.code` 대신 `error.code`만 읽었다.

운영에서는 고객 레시피를 읽거나 변경하지 않고 함수 정의의 단위 지원 여부와 마이그레이션 번호만 조회했다. 생성 함수의 tsp/tbsp/pack 지원은 모두 false, 재료 검토 함수의 tsp 지원은 true, 최신 적용 이력은 0056이었다. 진단 기록은 `.artifacts/shopping-create-production-inspection.json`에 있다.

## 변경 범위

- 장보기 준비 재진입 시 현재 레시피 재료와 저장 초안을 비교한다. 밥 120g·달걀 1개로 수정한 조리 원문을 반영하고 삭제한 재료는 제거한다. 변경되지 않은 재료의 선택·제외와 확인된 구매 입력은 재배치 후에도 유지한다. 원본이 바뀌면 생성 키를 새로 만들고, 동일 요청 재시도에는 같은 키를 유지한다.
- 조리량에서 자동 생성됐던 기존 초안의 구매 수량은 비워 사용자가 별도로 입력하게 한다. 구매 수량 확인 여부를 저장해 명시적으로 입력한 구매량과 구분한다. 분수·대분수 파서는 원문을 수정하지 않으며 장보기 구매량에 자동 적용하지 않는다.
- 장보기 준비의 각 재료 옆 편집 버튼으로 구매 재료명·수량·단위를 입력한다. 구매 수량을 몰라도 목록을 먼저 만들 수 있다. 구매 단위 변경 시 표준 환산을 수행하며, 환산 기준이 없으면 이전 숫자를 다른 단위로 그대로 옮기지 않는다.
- 새 마이그레이션 **0058_fix_shopping_create_units.sql**은 `create_kitchen_shopping_list(text,jsonb,uuid)`의 허용 단위를 DB 검토·완료 함수의 기존 37종 목록에 맞춘다. 이전 앱·기록과의 호환성을 포함한 서버 허용 목록이며 새 구매 선택지는 조리 계량 단위를 제외한 34종이다. 수량·단위를 모두 비워 목록에 담는 것도 지원한다.
- 구매 수량 정밀도를 소수점 6자리로 확장한다. 125g→0.125kg 같은 환산 결과가 0.13kg으로 반올림되지 않도록 장보기 항목 열과 `record_shopping_purchase(uuid,jsonb)`의 수량 검증·앱의 분배 계산을 함께 변경한다. 금액 정밀도와 과거 구매 기록은 변경하지 않는다. 입력 가능 정밀도를 넘는 새 수량은 안내 후 수정받으며 조용히 반올림하지 않는다.
- 오류 코드를 실제 서버 응답 구조에서 읽고 로그인 만료·서버 처리 실패·입력 확인 안내를 구분한다. 서버 원문과 내부 SQL은 표시하지 않는다. 한글·영어 문구를 제공한다.

## 검증

- 기존 로컬 DB 함수: `invalid kitchen shopping item quantity or unit` 오류 재현.
- 새 DB 함수: 37종 단위, 원문·수량 보존, 미확정 수량, `개` 별칭, 동일 요청 중복 방지, 밥·달걀 제외 후 양념만 생성 통과.
- 잘못된 단위·수량 쌍·소유자 주입은 전체 작업을 취소한다. 다른 회원 데이터와 익명 접근은 차단한다. 테스트 계정·목록 및 함수 변경은 모두 로컬 트랜잭션 종료 시 롤백했다.
- 핵심 Flutter 회귀 35개 및 전체 Flutter 311개 통과(기존 선택형 4개 건너뜀), 정적 분석 0건. 최신 조리 원문 표시, 별도 구매 수량 입력, 선택 제외, 생성 실패 후 재시도와 초안 삭제, 2팩→600g→0.6kg, 구매 이력과 조리 기록 분리, 한글·영어 문구를 검증했다.
- 마지막 정밀도 보강 후 장보기·구매·공급업체 요청서·분수·번역 관련 91개를 재검증해 모두 통과했다. 과거 보유 이력으로 자동 제외하지 않는 마지막 변경은 화면 회귀 3개와 해당 파일 정적 분석이 통과했다. 전체 재분석도 오류 0건이다.
- 로그: `.artifacts/shopping-fix-final-tests.log`, `.artifacts/shopping-fix-precision-tests.log`, `.artifacts/shopping-fix-stock-selection-tests.log`, `.artifacts/shopping-fix-precision-analyze.log`, `.artifacts/shopping-fix-stock-selection-analyze.log`. 수정 범위의 `git diff --check` 통과.
- 정밀도 DB 회귀: 0.125kg 목록 생성→실제 구매 기록→동일 요청 재시도에서 값을 정확히 보존한다. 이후 조리 기록을 추가해도 구매 기록·재고 수량이 변하지 않는다.

## 운영 반영 순서

1. 운영 함수 정의와 접근 권한을 다시 읽어 사전 점검한다.
2. 사용자 승인 후 **0058만** 트랜잭션으로 적용하고 마이그레이션 이력을 등록한다. 미배포 상태인 사전 모집용 0057은 이 수정에 필요 없으며 일괄 DB push를 사용하지 않는다. 변경은 장보기 수량 열의 정밀도 확대와 DB 함수 2개이다. 행 삭제·Edge Function 재배포는 필요 없다. 롤백 시에도 저장된 소수점 수량이 손실되지 않도록 열 정밀도를 다시 축소하지 않는다.
3. 운영 함수의 37종 단위 지원과 기존 접근 제한을 다시 확인한다.
4. 승인 후 앱 버전을 1.0.1+65로 올려 production 서명 AAB를 생성·검증한다. 사용자가 Play 경로로 직접 업데이트한다. 휴대폰 기존 앱 삭제나 데이터 초기화는 하지 않는다.
5. 업데이트한 앱에서 해당 비빔밥의 장보기 준비를 다시 열어 조리 원문 밥 120g·달걀 1개를 확인한다. 달걀 구매 10개 등 별도 구매량 입력, 구매 단위 환산, 선택 제외, 미입력 상태의 목록 생성 및 재진입을 확인한다.

DB 적용만으로 기존 앱의 단위 거부 오류도 해소되지만, 조리/구매 분리·저장 초안 동기화·새 구매 편집창에는 앱 업데이트가 필요하다. 실제 휴대폰 검증은 아직 수행하지 않았다.

## 승인 후 완료 기록

운영 DB 0058만 적용하고 실제 함수 원문·권한·RLS·소수점 6자리 정밀도를 검증했다. 전체 Flutter 311개 통과·기존 선택형 4개 건너뜀, 정적 분석 0건 후 production AAB를 생성했다. v64와 업로드 서명 일치 및 파일 무결성 검사도 통과했다. 자세한 파일·운영 증적은 [v65 배포 기록](release-v65.md)을 따른다.
