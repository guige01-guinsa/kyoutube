# 업소 메뉴판·레시피 출시·구매 연결

2026-09-22: v79 통합 배포에서 메뉴 후보, 별도 메뉴 선정 권한, 업체별 빠른 구매와 재고 예약을 추가했다. [최신 사용법](business-menu-fast-purchase.md) · [v79 배포·검증](release-v79.md). 아래 수동 구매 흐름도 계속 제공한다. 파일·검증 항목은 최초 v78 구현 당시의 기록이다.

## 사용 흐름

1. **업소 공동 업무 → 공동 레시피**에서 레시피를 개발합니다. 개인 레시피를 선택해 공동 레시피로 복사하는 기존 기능도 사용할 수 있습니다.
2. 기준 인분과 **구매 기준 재료**의 품명·규격·조리량·단위를 등록합니다. 등록한 값에서 읽기용 재료 목록을 생성하므로 구매 계산과 다른 재료 목록이 저장되지 않습니다. 기존 자유 입력 재료는 추정해서 자동 변환하지 않습니다.
3. 조리 담당자가 **시험 조리 결과 등록**으로 결과를 기록합니다. **메뉴 선정·출시·가격 관리** 권한을 받은 담당자 또는 사장이 **이 버전 출시 승인**을 누릅니다. 승인 후 수정 내용을 저장하면 새로운 개발 버전이 됩니다.
4. **메뉴판 관리 → 메뉴 등록** 또는 레시피 상세에서 개발 버전을 **메뉴 후보**로 담습니다. 후보는 가격 미정을 허용합니다. 승인된 버전과 확정 판매가로 **출시 준비 / 판매 중 / 판매 중지**를 관리하고 판매 중인 항목만 메뉴판 형태로 미리 볼 수 있습니다. 판매 메뉴 구매는 **판매 메뉴로 빠른 구매**에서 업체별로 한 번에 준비할 수 있습니다.
5. **메뉴·레시피에서 구매**에서 구매 목적을 선택합니다. 개발·시험용은 선택한 개발 레시피 버전, 출시 준비용은 승인된 레시피 버전, 영업용은 현재 판매 메뉴를 참조합니다.
6. 레시피·메뉴를 최대 20개 선택하고 조리할 인분을 입력합니다. 서버가 기준 인분에 맞춰 재료를 계산합니다.
7. 이번 공급업체에 보낼 재료를 선택하고 사용 가능 재고·미배정 입고 예정량·포장당 양·구매 단위를 확인합니다. 없는 재고/입고 예정량은 직접 0으로 입력합니다.
8. 공급업체명을 직접 입력하거나 내 등록 공급업체에서 선택합니다. 선택 시 업체명만 공동 요청서에 복사합니다. **구매 초안 만들기** 후 기존 편집기에서 납품일·단가 등을 확인하고 기존 구매 승인·전달·입고 확인 절차를 진행합니다.

예: 4인분에 양파 600g인 판매 메뉴를 30인분 준비하면 4,500g이 필요합니다. 사용 가능한 재고 1,000g, 미배정 입고 예정 0g, 한 봉지 2,000g이라면 2봉지를 구매하고 500g이 남습니다.

## 버전과 과거 자료 보존

- 개발 레시피, 판매 메뉴, 구매요청 작성 기준을 구분합니다. 메뉴는 `recipe_id + recipe_revision`과 당시 레시피 사본을 보관합니다.
- 레시피를 새 버전으로 저장해도 판매 메뉴의 배합은 자동 변경되지 않습니다. 새 버전의 시험 조리·출시 승인 후 메뉴 편집에서 연결을 바꿔야 합니다.
- 레시피 변경 이력에서 현재 버전과 제목·기준 인분·재료·조리법·메모의 차이를 비교합니다. 선택 창에는 최근 30개 버전을 표시합니다. 기존 메뉴가 연결한 더 오래된 버전은 계속 보존됩니다.
- 출시 승인과 시험 기록, 메뉴 이름·판매가·연결 버전·판매 상태 변경은 이력으로 남습니다. 이미 승인된 버전의 승인 상태를 덮어쓰지 않습니다.
- 구매 기준에는 출처 레시피/메뉴, 버전, 인분, 당시 재료량, 확인한 재고·입고 예정량, 포장 규격, 제외한 재료, 구매량과 여유량을 저장합니다. 이 기준은 구매 편집과 별개로 보존됩니다.
- 구매요청 메모에도 출처 레시피·버전·인분을 넣어 PDF에서 참조할 수 있습니다. 사용자가 메모나 구매 품목을 이후 수정해도 원래 계산 근거는 상세 화면에 남습니다.
- 판매 중인 메뉴에서 사용하는 레시피는 바로 사용 중지할 수 없습니다. 메뉴 판매를 먼저 중지해야 합니다.

## 계산과 적용 범위

- 재료명·규격·조리 단위가 같은 항목만 합산합니다. 대소문자와 앞뒤 공백만 정규화하고, 다른 손질 상태·규격·단위는 분리합니다. 동의어 추정이나 g↔kg 자동 변환은 하지 않습니다.
- 필요 구매량 = max(0, 필요 조리량 − 사용 가능 재고 − 입고 예정량). 포장 구매량은 필요 구매량/포장당 양을 올림합니다.
- 구매 계산에 입력하는 수량은 소수점 6자리까지 지원합니다. 인분 환산 합계는 조리 단위의 0.000001 단위로 올림한 뒤 포장량을 계산합니다. 화면의 포장 계산은 정수 단위 계산을 사용해 0.07/0.01이 8개로 표시되는 부동소수점 오차를 피합니다.
- 이 수동 계산 흐름의 재고 입력은 담당자가 확인하는 값입니다. v79의 **판매 메뉴로 빠른 구매**에서는 별도로 관리하는 재고를 연결하고 사용 가능량을 예약할 수 있습니다. 다른 작업에 이미 배정한 재고와 입고 예정량을 다시 차감하면 안 됩니다.
- 한 요청서는 한 공급업체를 사용합니다. 수동 흐름에서는 업체별 재료를 선택해 작성하고, v79 빠른 구매에서는 업체별 요청서를 일괄 생성하며 재고를 예약합니다. 진행 중 요청 수를 표시하지만 동일 발주 여부를 자동 판단하거나 기존 요청을 취소하지는 않습니다.
- 단가는 자동으로 만들지 않습니다. 생성된 초안은 기본 KRW이며 기존 편집기에서 통화·단가를 확정할 수 있습니다. 메뉴 판매가는 원가나 공급업체 단가로 간주하지 않습니다.
- 메뉴판은 로그인한 업소 직원의 내부 미리보기입니다. 고객용 공개 메뉴 URL·QR, 메뉴 이미지, 예약 시각 자동 출시, POS 연동은 포함하지 않습니다.
- 이번 기능은 DB 계산으로 동작하며 별도 AI 호출이나 외부 유료 API를 추가하지 않습니다. 기존 AI 검토 기능의 이용 한도는 그대로입니다.

## 권한과 안전장치

| 작업 | 필요한 기존 업소 권한 |
|---|---|
| 메뉴·레시피 열람 | recipes.read |
| 레시피 편집·시험 조리 기록 | recipes.write |
| 메뉴 후보 등록·수정 | recipes.read + recipes.write (또는 menus.approve) |
| 출시 승인·가격/판매 상태 변경 | recipes.read + menus.approve |
| 구매 기준 미리 계산 | recipes.read + purchasing.read |
| 구매 초안 생성 | recipes.read + purchasing.write |

- 사장은 기존 전체 권한을 사용합니다. 직원의 화면 선호 설정은 권한을 부여하지 않습니다. 기존 Business 이용권 제한과 구매 승인 정책을 유지합니다.
- 업소를 잠그고 변경을 처리하며 예상 revision 또는 시험 기록 ID가 다르면 충돌로 중단합니다. 생성 요청 ID를 같은 입력으로 재시도하면 같은 초안을 반환합니다.
- 새 4개 테이블은 RLS와 읽기 전용 회원 권한을 사용합니다. 인증 사용자의 직접 쓰기는 차단하고 RPC에서 업소·권한·소스·수량·승인 상태를 검사합니다.
- 개인 자료를 자동 공유하지 않습니다. 계정 전환 시 기존 편집 화면과 선택 창은 무효화됩니다.
- 기존에 구조화한 레시피를 구형 클라이언트가 자유 입력 문자열만 바꿔 저장하려 하면 차단합니다. 배합과 구매 계산 기준이 서로 달라지는 것을 막습니다.

## 파일과 운영 반영

- 마이그레이션: `supabase/migrations/0067_business_menu_lifecycle.sql`. 기존 이력 파일은 수정하지 않습니다. 0062의 업소 구조를 확장하고 설치된 검증·저장·중지 함수를 내부 전용으로 보존합니다. 0064는 의존성이 아닙니다.
- Flutter: `lib/features/business/domain/business_menu.dart`, `data/business_menu_repository.dart`, 메뉴 관리·재료 입력·구매 준비 화면, 기존 업소 레시피/구매 화면과 중앙 라우터.
- 운영 적용 완료: 기존 함수 정의/이력 보관 → 0067 트랜잭션 적용 → 운영 DB 권한·흐름 검사 → v78 웹 배포·서명 AAB 생성. 실제 직원 계정의 화면 조작과 휴대폰 설치 검증은 별도입니다.
- 새 Edge Function, API 키, 프로젝트 설정 변경은 없습니다. 릴리스 버전은 1.0.1+78로 올렸습니다.
